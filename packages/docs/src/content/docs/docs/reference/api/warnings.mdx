A malformed or incomplete recipe still compiles — the compiler and analyzer collect structured `Warning` objects instead of throwing, so callers can render a recipe and surface what's wrong at the same time. `WarningCode` and friends are exported from `@gram-lang/kitchen`.

## The `Warning` interface

```typescript
interface Warning {
  code: WarningCode;
  message: string;       // human-readable, ready to display as-is
  item?: string;
  loc?: { start: number; end: number }; // character offsets into the source, when available
  section?: string | null;
  data?: Record<string, unknown>; // since 1.5.0: what a tool needs to fix it (see below)
}
```

`compile()` returns them on `CompilationResult.warnings`; `analyze()` carries those through and may push additional ones onto the same array on `AnalyzedCompilationResult.warnings`. Never a bare string — `.message` is always present.

<Since v="1.5.0" /> Certain codes also attach structured `data` so tools and language-server quick fixes can act without parsing `.message`. Only `INVALID_QUANTITY` (`{ reason, suggestion? }`), `OZ_AFTER_VOLUME` (`{ suggestion }`), `SPACED_COMPOSITE` (`{ suggestion }`, since 1.5.2), `DEPRECATED_FRONTMATTER_KEY` (`{ key, suggestion, specifier? }`, since 1.6.0), `REFERENCE_TO_INGREDIENT` (`{ suggestion }`, since 1.6.0), a timer's `INVALID_DURATION` (`{ suggestion }` when Gram can tell, since 1.6.0) and ingredient `INVALID_UNIT` (`{ reason, suggestion? }`) populate `data`.

## Severity & `--strict`

```typescript
type WarningSeverity = "error" | "warning" | "info";
const warningSeverity: Record<WarningCode, WarningSeverity>;
```

Structural integrity issues — a reference to something that doesn't exist, a naming collision, or an unresolvable module — are `error`. Recoverable gaps (estimation gaps, incomplete annotations) are `warning`, and contextual notifications (surplus quantities, batch scaling, resource contention) are `info`. This is exactly the distinction the CLI's `gram check --strict` flag uses: without `--strict`, only `error`-severity codes fail the command; with it, every `warning` and `info` is promoted to `error` too. Build your own strict-mode logic on `warningSeverity[code]` the same way.

<Since v="1.6.0" /> `warningInfo` holds the same severity with what else a tool needs to know of a code: `deprecated: true` marks a code that flags a deprecated form (`DEPRECATED_FRONTMATTER_KEY`), which the language server shows struck through. `warningInfoOf(code)`, exported by `@gram-lang/modules`, reads it for any code, module codes included.

```typescript
interface WarningCodeInfo { severity: WarningSeverity; deprecated?: true }
const warningInfo: Record<WarningCode, WarningCodeInfo>;
```

## Codes

<GeneratedTable table={warningCodesTable("en")} />

### `VARIABLE_NOT_FOUND`
A relative quantity references an intermediate variable (`50% of &name`) that hasn't been declared as an intermediate output (`->&name`) anywhere in the recipe. **Fix**: declare the variable before referencing it, or check for a typo in the name.

### `RELATIVE_QUANTITY_UNRESOLVED`
A relative quantity references an ingredient (`50% of @name`) that hasn't appeared earlier **in the same section** — relative-to-ingredient targets are section-scoped, unlike variables. **Fix**: move the referenced ingredient earlier in the same section, or reference a variable (`&name`) instead if it's meant to be recipe-wide.

### `RELATIVE_QUANTITY_UNKNOWN_MASS`
Pushed during analysis: the target of a relative quantity was found, but its own mass couldn't be computed (no resolvable unit/density), so the percentage can't be applied. **Fix**: give the target ingredient a standardizable unit, or a density/`unit_weight` entry in the ingredient database.

For a [ratio with units](/docs/reference/syntax/relative-quantities/#ratios-with-units) (`1 / 100 g @&flour`, `~{15 min / 500 g @&roast}`, <Since v="1.5.0" />), it includes a `reason` pointing to the ratio and leaves the amount unresolved:
- `noTargetQuantity`: the target has no quantity.
- `incompatibleUnits`: mismatched counts (`2 slices` against cloves), a weight against a named piece, or trailing words (`100 g of`).
- `missingDensity` / `missingUnitWeight`: converting between weight and volume or pieces requires `density` or `unit_weight` in the database.
- `wholeUseAmbiguous` / `producerMassUnknown`: for an intermediate used whole (`&dough`), either another section also consumes it or the producing section's mass is incomplete.
- `stepProducer`: the intermediate used whole is made by a step (`Mix … ->&dough`), not by a whole section, and only a section's mass is weighed. Write the amount used (`&dough{500 g}`), or make it in its own section.

**Fix**: match the target's unit, add `density` or `unit_weight` to the database, or specify the intermediate's used quantity (`&dough{500 g}`).

### `CIRCULAR_REFERENCE`
An ingredient's relative quantity targets itself (`@flour{50% of @flour}`). **Fix**: remove the self-reference — a percentage-based quantity must target a *different* ingredient or variable.

### `UNDEFINED_REFERENCE`
A bare reference (`&name`) or a referenceable ingredient (`@&name`) points to something that was never registered earlier in the recipe. **Fix**: introduce the ingredient (without `&`) before referencing it, or check for a typo.

### `REFERENCE_TO_INGREDIENT`
<Since v="1.6.0" />

A reference (`&flour`) names a raw ingredient written earlier (`@flour{500 g}`), not an intermediate: `&` is for what a step or a section produces (`->&dough`), `@&` for a later mention of an ingredient. The recipe compiles as before. **Fix**: write `@&flour`; `data.suggestion` holds it, and the language server's quick fix adds the `@`. An intermediate that shares an ingredient's name (`Brown @chicken{1} ->&chicken.` then `&chicken`), or a `@use … as &name` binding, raises nothing.

### `MISSING_UNIT`
A `Timer` or `Temperature` was written without an explicit unit (e.g. `~{10}` instead of `~{10 min}`). **Fix**: add an explicit unit.

### `INVALID_UNIT`
Emitted in four situations:
- **Time or temperature units**: a word after a number in a `Timer` or section anchor is not a recognized time unit (`~{3 bananas}`), or a `Temperature` uses a unit other than Celsius or Fahrenheit. **Fix**: use a recognized time unit (`h`, `hr`, `min`, `heures`…), or `°C` / `°F` for temperatures.
- **Unjoined quantities in a unit** <Since v="1.5.0" type="changed" />: an ingredient's unit looks like two quantities without an operator (`@flour{1 cup 5 tbsp}` or `@flour{1 kg 200 g}`), where `cup 5 tbsp` would otherwise be treated as one unknown unit with no mass. **Fix**: write it as a [sum](/docs/reference/syntax/ingredients/#sums-of-quantities) (`@flour{1 cup + 5 tbsp}`); `data.suggestion` provides the corrected unit (`cup + 5 tbsp`) for editor quick fixes. Descriptive unit text like `@tomatoes{1 tin of 400 g}` is unaffected.
- **Leading prose before a number**: a unit hides a leading word before the number (`@flour{about 200g}`), since quantities must start with a number. **Fix**: write `@flour{200g}` and keep `"about"` in the prose. Pure text quantities (`{a pinch}`, `{to taste}`) raise nothing.
- **Cooklang's separator** <Since v="1.6.0" />: a `%` between the number and a unit of mass or volume (`@flour{200%g}`, `reason: "cooklangSeparator"`), which would otherwise read as an unknown unit `%g` with no mass. **Fix**: write `@flour{200 g}`; `data.suggestion` holds the unit (`g`) and the language server's quick fix puts a space in place of the `%`. A `%` before any other word (`{70 % cacao}`) is left alone.

### `INVALID_QUANTITY`
<Since v="1.5.0" />

Emitted when a [sum of quantities](/docs/reference/syntax/ingredients/#sums-of-quantities) or number expression cannot be evaluated. The recipe still compiles and renders the text as written, but the value is excluded from shopping list and nutrition totals. `data.reason` identifies the cause:

| `reason` | Example | Fix |
| :--- | :--- | :--- |
| `unitlessTerm` | `{1 + 1 cup}` | Give every term a unit (`{1 cup + 1 tbsp}`). |
| `percentTerm` | `{100 g + 10%}` | Write the computed total (`{110 g}`, provided in `data.suggestion`) or use a relative quantity (`{10% &flour}`). |
| `expressionTerm` | `{2 x 100 g + 50 g}` | Sums only support `+` and `-`; write `{250 g}`. |
| `quantityInUnit` | `{1 tin of 400 g + 50 g}` | Express the amount in a single unit (`{450 g}`). |
| `nonPositiveTotal` | `{1 tbsp - 1 cup}` | Subtracted amount equals or exceeds what was added. |
| `rangeAfterMinus` | `{1 cup - 1-2 tbsp}` | Put ranges on added terms, or write the total as a range. |
| `minusAcrossFamilies` | `{1 cup - 20 g}` | Subtract only from the same unit family (volume from volume, weight from weight). |
| `zeroDenominator` | `{1/0 cup}`, `{1/0% &dough}`, `#pan{1/0}`, `^{1/0 °C}` | Division by zero is ignored; write a valid fraction (`1/2`). |
| `zeroRatioDenominator` | `{2 g / 0 g @&flour}`, `~{15 min / 0 g @&roast}` | A ratio per nothing is ignored; write the amount it is per (`/ 100 g`). |
| `relativeNotSupported` | `@eggs{3}<@box{50% @&flour}`, `@eggs{1}<@box{1 / 100 g @&flour}` | Percentages and ratios are not supported on composite parents yet; specify the parent's quantity (`@eggs{3}<@box{1}`). |

Subtraction is checked per unit family: `{1 cup - 2 tbsp + 30 g}` is valid (2 tbsp are subtracted from 1 cup), while `{1 cup - 20 g}` has no weight to subtract from.

### `OZ_AFTER_VOLUME`
<Since v="1.5.0" />

Informational notice when `oz` follows a volume in a sum (`@water{1 cup + 2 oz}`). Because `oz` denotes weight, Gram keeps it separate from the volume. **Fix**: change to `fl oz` if fluid ounces were intended (`data.suggestion` offers this quick fix).

### `SPACED_COMPOSITE`
<Since v="1.5.2" />

Spaces around the composite operator (`@lemon zest{1} < @lemon{2}`, or a space on one side only). With them, the line reads as two separate ingredients with a `<` in the prose between them: the lemon is bought on top of the zest's own entry, two lemons too many on the shopping list. The recipe still compiles as written. **Fix**: glue `<` to both ingredients (`@lemon zest{1}<@lemon{2}`); `data.suggestion` holds the operator glued to the parent (`<@lemon`), which the language server's quick fix writes in place of the gap, and `gram format` makes the same repair.

### `DURATION_OUT_OF_RANGE`

A timer or a section's retro-planning offset lasts longer than 1000 years. **Fix**: check the number, often a stray digit or a missing unit letter (`~{-3000d}` is eight years, `~{-3000000000d}` is not a recipe). The duration is capped at 1000 years, so the timeline stays finite instead of coming out as `0`, `Infinity` or `NaN`. That limit is a technical bound, not a judgement on recipes: anything up to it, a solera that runs for decades included, is planned as written and raises nothing.

### `AMBIGUOUS_NUMBER`
<Since v="1.5.0" />

A comma followed by three digits after one to three integer digits (`@flour{1,000 g}`, `@flour{12,500 g}`). Because Gram supports decimal commas and has no thousands separator, `{1,000 g}` is parsed as `1 g` (and `{12,500 g}` as `12.5 g`). Checked across quantities, timers, temperatures, percentages, and section anchors (including on `@use`). **Fix**: write `{1000 g}` if a thousand was meant, or `{1 g}` otherwise. Periods (`{1.000 kg}`) always parse as decimals without warning.

### `INVALID_DURATION`
<Since v="1.5.0" />

A timer or section anchor uses numbers and units Gram recognizes, but in an ambiguous or unsupported shape:
- **Ambiguous or malformed timers**: `~{1:30}` (hours or minutes?), `~{30min 1h}` (wrong order), `~{1h75}` (`≥ 60` after hours), `~{1-2h30}` (ambiguous range bound), `~{2-1 h}` (reversed range), `~{2 * 2 min}`, or prose (`~{half an hour}`). The timer is excluded from total time while keeping its `raw` string.
- **Unsupported anchors**: ranges (`~{-1-2d}`), seconds (`~{-1min30}`, `~{-5'}`), or proportional anchors (`reason: "anchorRatio"`).
- **Proportional timer limits**: multipliers (`~{15 min / 500 g @&roast * 2}`, `reason: "ratioMultiplication"`) or ranged targets (`~{15 min / 1-2 kg @&roast}`, `reason: "ratioShape"`).

**Fix**: follow the suggested format in `.message` (e.g. `~{1h30}`, `~{1:30 min}`, `~{1h30-2h}`). <Since v="1.6.0" /> For Cooklang's separator (`~{15%min}`), `data.suggestion` holds the duration Gram reads once the `%` is a space (`15 min`), which the language server's quick fix writes in the braces. Unknown units after a number still raise `INVALID_UNIT`, and bare numbers raise `MISSING_UNIT`.

### `DEPRECATED_FRONTMATTER_KEY`

<Since v="1.6.0" /> The frontmatter uses a deprecated key, removed in 2.0.0: `servings` (write `portions`), `yield` or `yields` (write `makes`). It is raised even when the key to write is also there (that one wins). The warning carries no `loc` (the AST keeps no position for the frontmatter's keys) but `data: { key, suggestion }`: the language server shows it struck through on the key and offers to rename it, or to remove its line when the key to write is already there. Raised by an imported module, `data.specifier` names it and the diagnostic stays on its `@use` line. **Fix**: rename the key as the message says. See [Deprecated features](/docs/how-to/deprecations/).

### `SCOPE_CONFLICT`
Two sections declare the same intermediate/global variable name (`->&name`). Variable names must be unique across the whole recipe, not just within a section. **Fix**: rename one of the two declarations.

### `MISSING_INGREDIENT`
During nutrition estimation, an ingredient with a computable mass has no matching entry (by id or alias) in the ingredient database at all. **Fix**: add the ingredient (or an alias to an existing entry) to your database.

### `MISSING_MACROS`
The ingredient exists in the database, but its entry has no `nutrition` block. **Fix**: add a `nutrition` block to that database entry.

### `UNKNOWN_MASS`
Nutrition estimation couldn't compute a mass for this ingredient at all (unresolvable unit, no density/`unit_weight`), so it's excluded from the totals. **Fix**: same as `RELATIVE_QUANTITY_UNKNOWN_MASS` — give it a standardizable unit or physical data in the database.

### `INVALID_MODIFIER_COMBINATION`
Conflicting or duplicated modifiers on the same ingredient/cookware — e.g. `optional (?)` with `important (*)`, `hidden (-)` with `important (*)`, `hidden (-)` with `referenceable (&)`, or the same modifier twice. The specific combination is named in `.message`. **Fix**: remove the conflicting modifier.

### `INVALID_BAKERS_REFERENCE`
The ingredient marked as the baker's-percentage base (via the `*` modifier or the `bakersReference` option) has a mass that was itself derived from *another* ingredient's relative quantity — it can't also serve as the 100% anchor, since that would be circular. **Fix**: mark a different ingredient with an absolute (non-relative) quantity as the reference.

### `NO_BAKERS_REFERENCE`
Baker's math was explicitly requested (`enableBakersMath` with a bare `*` search, or an explicit `bakersReference` id) but no ingredient matched. **Fix**: mark an ingredient with the `*` modifier, or correct the `bakersReference` id to match an existing ingredient.

### `MULTIPLE_BAKERS_PERCENTAGE`
<Since v="1.5.1" /> More than one ingredient is marked as the baker's-percentage base (`@*flour{500 g}` and `@*rye{100 g}`). The first one marked stays the base; the others lose their `*` and the rest of the recipe compiles as usual. The same ingredient marked twice is the same base and raises nothing. **Fix**: keep the `*` on a single ingredient.

### `COMPOSITE_PARENT_CONFLICT`

A short composite child name (e.g. `@juice`) is drawn from two different parent ingredients within the same recipe (e.g. `<@lemon` in one step and `<@orange` in another). **Fix**: use the full name for the child (e.g. `@lemon juice` and `@orange juice`) to prevent database identity collisions.

### `MODULE_NOT_FOUND`

An imported module specified in a `@use` directive could not be resolved or found on the filesystem. **Fix**: verify the module path, file extension (`.gram`), or configured path aliases in `config.yaml`.

### `DAY_OVERFLOW`

A working day (derived from a section's `~{-Nd}` anchor) starts before its 24-hour window opens because a long passive rest pushes it backward. **Fix**: anchor the section further back (for example `~{-2d}` instead of `~{-1d}`), or shorten the rest duration.

### `TIME_PARADOX`

During ALAP reverse scheduling, a producing task is pulled earlier than the beginning of the recipe to satisfy an intermediate consumption deadline or serving time. Gram rebases the timeline to start at zero. **Fix**: check whether active steps and rest intervals before the deadline fit realistically within the available timeframe.

### `TRACK_CONTENTION`

Multiple passive timers share the same equipment track (e.g. `~_oven`) and cannot execute simultaneously. The scheduler serializes them sequentially to prevent equipment collision, delaying the second task. **Fix**: this is an informational notice; if you have access to multiple appliances, assign them distinct track names (e.g. `~_oven1` and `~_oven2`).

### `PASSIVE_OVERLAP_SAME_COOKWARE`

Two passive timers overlap in time, in steps that cite the same cookware (`#oven` in both), with no named track in common. If one is meant to follow the other, they are probably on one oven: the plan shows them side by side. **Fix**: give them the same named track (`~_oven{30min}` then `~_oven{20min}`) so they take turns; if both fit in the oven at once, this is only an informational notice. Only names are compared (`#oven` with `#oven`), so it works whatever the language of the recipe, and the overlap is read on the default timeline.

### `MODULE_PARSE_ERROR`

A module imported by `@use` does not parse, so none of its sections can be spliced in. On the checked document itself, the message is the parser's own. **Fix**: open the imported file and fix the syntax error the message quotes.

### `MODULE_CYCLE`

Two or more modules import each other, directly or through others (`a.gram` imports `b.gram`, which imports `a.gram`). The message lists the chain. **Fix**: move what both need into a third module that imports neither.

### `MODULE_DEPTH_EXCEEDED`

The chain of imports is deeper than Gram follows. **Fix**: flatten the chain: import the base directly from the recipe that needs it.

### `MODULE_EXPORT_NOT_FOUND`

A binding of `@use` names something the module does not export (`as &sauce` when the module's sections export `&base`). Only a section-level `->&name` is exported: when the name exists in the module as a step-level `->&`, the message says it is not re-exported, and the language server offers to add `->&name` to the header of the section that declares it, in the module. Otherwise it suggests the closest export. **Fix**: use one of the listed exports, or export the name from the module.

### `UNUSED_IMPORT`

A binding of `@use` is never used in the recipe. **Fix**: use it (`&name`), or remove it from the `@use` line.

### `UNRESOLVED_MODULE_YIELD`

The recipe asks for a quantity of an imported intermediate (`&dough{300 g}`), but the module's yield cannot be weighed: one of its ingredients has no known mass. The module cannot be scaled to the quantity asked. **Fix**: give that ingredient a mass, or a density or unit weight in the ingredient database.

### `ESTIMATED_MODULE_YIELD`

The module's yield was weighed with standard densities or unit weights, so the scale factor applied to it is an estimate. **Fix**: write the module's ingredients in grams for an exact factor, or accept the estimate.

### `MODULE_UNIT_MISMATCH`

The recipe asks for an imported intermediate in a unit the module's yield does not convert to (a volume for a yield in grams, with no density). **Fix**: ask for it in the unit of its yield, or give the module a density.

### `MODULE_BATCH_INTERPRETATION`

An imported intermediate is asked for with a number and no unit (`&dough{2}`): it is read as that many batches of the module. **Fix**: an informational notice; write a unit to ask for a quantity instead.

### `IMPORTED_BAKERS_REFERENCE_DROPPED`

The module marks a baker's-percentage base (`@*flour`), which stays scoped to the module: the importing recipe does not inherit it. **Fix**: an informational notice; mark a base in the importing recipe if it needs one.

### `DENSITY_OVERRIDE_SHADOWED`

The importing recipe and the module both override the density of the same ingredient (`densities:`), with different values: the importing recipe's value wins. **Fix**: an informational notice; keep a single value if the difference is not meant.

### `MODULE_SURPLUS`

Several bindings of one `@use` are asked for in quantities that do not match the module's proportions: the module is scaled for the one that needs the most, so another one comes out larger than the recipe uses. The message gives the surplus. **Fix**: an informational notice; adjust the quantities if the surplus is not meant.

### `MODULE_SPECIFIER_INVALID`

The path of a `@use` has a shape Gram does not read: an absolute path (`/home/…`, not portable), a `hub:` path (not supported yet), a path that starts with neither `./`, `../` nor `@…/`, or one that does not end in `.gram`. The message gives the reason. **Fix**: write a relative path, `@/…` from the project root, or `@alias/…` with an alias declared under `paths:` in `.gram/config.yaml`.

### `MODULE_SCHEME_UNSUPPORTED`

The path of a `@use` is a URL (`https://…`, or any other `scheme://`): modules are read from the project only. **Fix**: copy the module into the project and import it by its path.

### `STOCKED_RETRO_PLANNING_IGNORED`

A module imported as stock (`--stock`) carries a retro-planning offset (`~{-1d}`): a stocked item is already made, so the offset is ignored. **Fix**: remove the offset, or import the module without `--stock` to schedule its preparation.

### `RETRO_PLANNING_OVERRIDE_SHADOWED`

The `@use` line sets a retro-planning offset that replaces the one the module sets itself. **Fix**: an informational notice; keep one of the two if the difference is not meant.

### `MODULE_BINDING_SHADOWS_INGREDIENT`

The local name of an imported intermediate is also the name of an ingredient of the database (`as &butter`), which makes the two easy to confuse in the nutrition and the shopping list. **Fix**: give the binding another local name (`as &brown_butter`).

### `STOCKED_DESTRUCTURED_NUTRITION_BLENDED`

A stocked module is imported with several bindings (`as { &a, &b }`): its nutrition is known for the whole module only, so each binding gets the module's average profile. **Fix**: an informational notice; split the module if each part needs its own nutrition.

## Codes of the lint layer

<Since v="1.6.0" /> The language server reads its diagnostics from `@gram-lang/modules/lint` (experimental, see the [Modules API](/docs/reference/api/modules/#lint)), which reports the compiler's warnings above and adds checks of its own, found in the source rather than in the compiled recipe. Their severity can also be `hint`, which never fails a build, even under `--strict`. Each diagnostic links to its section of this page.

### `PARSE_ERROR`

The document does not parse: the message is the parser's, at the place it stopped. No other diagnostic is reported until it parses. **Fix**: correct the syntax at the place shown.

### `COMPILE_ERROR`

The document parses, but compiling or analyzing it failed (a scale that cannot be applied, say). It is shown at the top of the file. **Fix**: correct what the message names.

### `MISSING_TITLE`

The frontmatter has no `title:` (or there is no frontmatter). The views fall back to a generic title. When the file opens a frontmatter, the language server offers to add the key. **Fix**: add `title: …` to the frontmatter.

### `UNUSED_INTERMEDIATE`

A step declares an intermediate (`->&sauce`) that no step uses, neither as a reference (`&sauce`) nor as the target of a share, a ratio or a proportional timer (`@salt{2% &sauce}`). One declared on a section heading is never reported: it is what a module exports, or the name of the finished dish. The language server offers to remove it. **Fix**: use it, or remove the `->&`.

### `UNKNOWN_INGREDIENT`

An ingredient is not found in the ingredient database, resolved as the nutrition resolves it (its name, its aliases, the same slug). Only checked when a database is loaded. The language server offers the closest name of the database (the first, when several are as close), never as the preferred fix: renaming an ingredient changes the recipe, so neither an editor's auto fix nor `gram check --fix` applies it. A second fix, never preferred, adds the ingredient to the database the editor reads (the file named by `database:` in `.gram/config.yaml`, else `.gram/ingredients.yaml`): an entry with its `name` and a commented skeleton of the fields to fill in (aliases, category, allergens and diets as `tags`, density, unit weight, nutrition per 100 g). It is not offered when the database already has an entry under that name. **Fix**: correct the spelling, or add the ingredient (or a plural, in its `aliases`) to the database.

### `LOST_INGREDIENT`

An ingredient is written but never read: a `//` earlier on the same line turned the rest of it into a comment, so `Mix @flour{200 g} // to taste, @salt{}` has no salt, in the shopping list or anywhere else. Only a `//` in the middle of a step counts: a whole `//` line and a `/* … */` block are comments written on purpose. No fix is offered, since only the author knows whether the comment or the ingredient is the mistake. **Fix**: move the comment to its own line, or end it before the ingredient.

### `MERGED_STEP_LINE`

A line meant to start a new block is read as more text of the step above, because a single line break does not end a step: a line opening with `[Action]` (the action of the next step), a `## …` line (the section vanishes), or any line after one ending with `->&name` (the step's output, after which another step was most likely meant). A plain line break inside a step stays valid (`A step,` then `the same step.` on the next line), and a line that could not open a block on its own is left alone (a bare `[Action]` with nothing after it, a `## …` with text after its `~{…}`): a blank line would only make it a syntax error. The language server offers to insert the blank line, as the preferred fix. **Fix**: leave a blank line before the line.

### `SUSPECT_INGREDIENT_NAME`

The name of an ingredient written with braces reads like a sentence: it holds `, `, `; `, `. ` (after a word of four letters or more, so `St. John's wort` is left alone), `、` or `。`, or it has more than 6 words or more than 40 characters. Only a hint: `@dark chocolate 70%, in drops{200 g}` is a valid name, but `drops` most likely belongs in the preparation. Where a break splits the name, the language server offers, never as the preferred fix, to move the rest into parentheses: `@dark chocolate 70%{200 g}(in drops)`. **Fix**: keep the name short, and the rest in the preparation.

### `UNREAD_FRONTMATTER`

The file opens a `---` block with keys, but the recipe has no metadata at all: a line the frontmatter does not accept, a `# …` comment or an indented line (`  - flour: 0.55`), made the whole block plain text of a step, title included. Shown on that line; `MISSING_TITLE` is then left out when the block writes a `title:`. On a `# …` line, the language server offers to remove it (not as the preferred fix); never on an indented line, which holds data. **Fix**: remove the comment, and write lists inline (`densities: [flour:0.55, milk:1.03]`).

## Configure the lint

<Since v="1.6.0" /> A project tunes the checks of the editor and of [`gram check`](/docs/reference/tooling/cli/#gram-check-pattern) in `.gram/config.yaml`: a code can be turned off, or shown at another severity (`hint`, `info` or `warning`). An `error` is never turned off nor lowered, so a broken recipe cannot be hidden.

```yaml
lint:
  rules:
    UNKNOWN_INGREDIENT: off
    UNUSED_INTERMEDIATE: hint
```

A single block can also be left out with a `// gram-ignore` comment on its own line, naming one or more codes:

```gram
## Sauce

// gram-ignore UNUSED_INTERMEDIATE
Reduce @stock{200 ml}. ->&reduction
```

The comment covers the block right after it: a whole step, however many lines it spans, or the line of a section heading (not the steps below it). Several `// gram-ignore` lines in a row add up. A bare `// gram-ignore`, with no code, does nothing. Diagnostics outside any step or heading (the frontmatter, the `@use` lines, those shown at the top of the file) cannot carry one: a comment cannot be written there without changing the file's meaning, so they are set in `.gram/config.yaml`. Never write `// gram-ignore` at the end of a step's line: `//` there turns the rest of the line into a comment.
