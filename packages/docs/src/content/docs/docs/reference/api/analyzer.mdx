Enriches a `CompilationResult` (from `@gram-lang/kitchen`) with physical properties — standardized mass, purchasing yield, nutrition estimates, and baker's percentages — by cross-referencing an ingredient database. This is the only stage in the pipeline that requires a database; parsing and compilation operate purely on any `.gram` source text without any external dependencies.

## `analyze`

```typescript
function analyze(
  result: CompilationResult,
  database: Record<string, IngredientData>,
  options?: AnalyzerOptions,
): AnalysisResult

interface AnalysisResult {
  result: AnalyzedCompilationResult;
  missingIngredients: string[]; // ids present in the recipe but absent from `database`
}
```

```typescript
import { compile } from '@gram-lang/kitchen';
import { analyze } from '@gram-lang/analyzer';

const compiled = compile(ast);
const { result: analyzed, missingIngredients } = analyze(compiled, myIngredientDatabase);
```

> The ingredient database is the **second positional argument**, not a field on `options` — `analyze(compiled, database, options?)`.

`analyze()` is a pure function that never mutates its `result` argument. `AnalyzedCompilationResult` extends `CompilationResult` — same shape, plus per-usage `normalizedMass`, `conversionMethod`, `isEstimate`, `purchasingMass`, and `bakersPercentage` fields, along with a `metrics.nutrition` block. See [Data formats](/docs/reference/api/data-formats) for a fully annotated example.

### `AnalyzerOptions`

All enrichment flags default to enabled (via internal `!== false` checks) — pass explicit `false` to opt out of a given enrichment pass.

| Option | Type | Description |
|---|---|---|
| `enableMassStandardization` | `boolean` | Convert ingredient quantities into standardized grams. |
| `enableYieldCalculation` | `boolean` | Apply the ingredient database's `physical.yield` (waste/prep factor) when standardizing mass. |
| `enableNutritionalEstimation` | `boolean` | Compute `metrics.nutrition` (calories and macronutrients, globally and per-portion). |
| `enableBakersMath` | `boolean` | Compute `bakersPercentage` relative to the `*`-marked (or `bakersReference`) ingredient. |
| `bakersReference` | `string` | Explicit ingredient id to use as the 100% baker's-percentage base, instead of the `*` modifier. |
| `portions` | `number` | Overrides the recipe's own `portions:` frontmatter as the divisor for `metrics.nutrition.perPortion`. |
| `lang` | `string` | Optional locale code (e.g. `'en'`, `'fr'`) for locale-scoped unit normalization and category sorting. |

## `validateIngredientDatabase`

```typescript
function validateIngredientDatabase(rawDb: unknown): {
  data: Record<string, IngredientData>;
  rejected: { key: string; message: string }[];
}
```

Validates entry-by-entry rather than all-or-nothing: one malformed ingredient does not prevent valid entries from loading. Pass `data` to the pipeline and surface `rejected` issues to the user (e.g. via `gram db validate`). See [Data formats](/docs/reference/api/data-formats) for the `IngredientData` YAML schema.

## Mass utilities

```typescript
function standardizeMass(
  amount: number,
  unit: string,
  database: Record<string, IngredientData>,
  ingredientName?: string,
  overrides?: Record<string, number>, // slug -> density (g/mL) or unit weight (g), from frontmatter `densities:`
  lang?: string,
): { mass: number; method: "physical" | "density" | "unit_weight" | "default" | "explicit"; isEstimate: boolean } | null

function convertUnit(value: number, fromUnit: string, toUnit: string, density?: number, lang?: string): number | null

function applyYield(
  mass: number,
  method: "physical" | "density" | "unit_weight" | "default" | "explicit",
  yieldFactor?: number,
): { normalizedMass: number; purchasingMass?: number }
```

`standardizeMass` resolves a quantity to grams via the following priority cascade: (1) direct mass units (`g`, `kg`, `oz`...), (2) volume units converted through the ingredient's resolved density, (3) count units (`clove`, `slice`...) converted via the ingredient's `unit_weight`. It returns `null` — never guessing blindly — when a volume unit has no resolvable density.

`convertUnit` converts between two arbitrary unit strings, bridging mass↔volume families when a `density` (expressed in g/mL) is provided. It returns `null` when a cross-family conversion is impossible without density data.

## `calculateNutrition`

```typescript
function calculateNutrition(
  ingredients: AnalyzedUsage[],
  database: Record<string, IngredientData>,
  portions?: number,
  massStatus?: 'precise' | 'estimated' | 'incomplete',
): NutritionMetrics
```

Flattens composite ingredients and alternatives (taking the first option), skips `optional`-modifier and zero-quantity items, and sums `nutrition` values (declared **per 100g** in the database — see [Data formats](/docs/reference/api/data-formats)) scaled by each ingredient's standardized mass. Returns `isEstimate: true` if any contributing mass was itself an estimate, and a `coverage` ratio (0–1: fraction of ingredients with known nutrition profiles).

`NutritionMetrics` provides the nutritional profile across three complementary bases:

```typescript
interface NutritionMetrics {
  total: Macros;          // the entire recipe, at its compiled or scaled quantities
  perPortion?: Macros;    // calculated whenever a portion count is known
  per100g?: Macros;       // per 100 g of recipe mass that contributed to macros
  portions?: number;      // the divisor applied to derive perPortion
  basis?: { mass: number; massStatus?: 'precise' | 'estimated' | 'incomplete' };
  isEstimate: boolean;
  coverage: number;
  warnings?: Warning[];
}
```

Every basis is derived directly from unrounded raw sums and rounded independently, preventing compounding rounding discrepancies between the total and individual portions. The `basis` property represents the mass denominator used for the `per100g` calculation — see [Nutritional estimation](/docs/explanation/nutrition/) for details on why this distinction matters when no cooking loss is modelled.

The list of tracked nutrients, their units, and their precision rules are defined in a single exported `NUTRIENTS` table, ensuring strict parity between `gram db enrich`, `gram db lint`, `gram db search`, editor hover hints, and all visual renderers.

## `diffRecipes`

```typescript
function diffRecipes(a: CompilationResult, b: CompilationResult): DiffResult
```

Computes the structural diff between two compiled recipes (e.g. two revisions of the same recipe file, or an unscaled baseline compared to its scaled counterpart). It tracks changes in ingredient quantities and units (with `percentChange`), preparation updates, schedule deltas (`totalTime`, `idleTime`, `activeTime`, `preparationTime`), added, removed, or modified sections, timer and temperature adjustments, and frontmatter (`meta`) changes. The `hasChanges` property evaluates to `true` whenever any diff category is non-empty.

The timing deltas compare durations from the default schedule (`schedule`): `totalTime`, `idleTime`, `activeTime`, and `preparationTime` all originate from `schedule`. An active timer defined as a range (`~{20-25min}`) counts on its longest bound for safety. These baseline metrics are identical on both sides of the comparison and match the default layout shown in `gram view`. *(Since 1.4.0. Earlier versions read the deprecated `metrics.totalTime` and `metrics.idleTime`, which reflected the legacy "all prep upfront" plan).*

A section spliced in from a modular `@use` import (`ProcessedSection.module` populated) is isolated from step-level section comparisons — preventing a single imported module from offsetting subsequent section indices and reporting false-positive diffs. Its import statement is compared independently by `(uri, binding, scale factor)` inside the `modules: ModuleDelta[]` array — any re-bound or rescaled module is flagged with `"changed"`.
