You can define `~timer` declarations and durations in your recipes using the `~` symbol.

## Basic declaration

A `~timer` **must** specify an explicit unit inside the braces. Fuzzy prose such as `~{about 10 minutes}` is invalid and rejected by the parser.

```gram
Bake for ~{25min}.
```

**Supported units:**
- `min` (minutes) - Canonical preferred standard.
- `h` (hours).
- `d` (days).
- `s` (seconds).

:::note
Shorthand `m` or the word `minutes` are automatically normalized to `min` by the compiler.
:::

These units are resolved through Gram's multi-language time dictionary: localized aliases below are recognized natively regardless of the recipe language (e.g. in a French recipe, `~{2j}` resolves identically to `~{2d}`).

### Timer names
You can assign an explicit name to a `~timer`. This is especially useful for passive background tasks: when multiple timers run concurrently (like a dough fermenting while a stock simmers), named timers allow user interfaces and production run sheets to track each process simultaneously without confusion.

```gram
Boil @eggs{2} for ~eggs{3min}.
```

### Exact times and ranges
<Since v="1.4.0" />

By default, a timer is **exact**: `~_{12h}` lasts exactly 12 hours. When an operation has variable or flexible duration, specify an interval: this provides official elasticity for Gram's scheduling engine.

```gram
Let the dough rest in the fridge ~_{12-24h}.

Roast the chicken for ~{40-50min}.
```

The interpretation of a range differs fundamentally based on timer type:

- **A passive range represents elasticity.** The declaration `~_{12-24h}` states: "ready from 12 hours, optimal up to 24 hours". By default, the timeline lays out the shortest bound (`'shortest'`). You can select alternative elasticity strategies (`'shortest'`, median `'balanced'`, or longest `'longest'`) via the `--rests` CLI option, the `gram.rests` VS Code setting, or the `rests` renderer option. When provided with a target serving time and kitchen availability, the scheduler uses this elasticity to bridge overnight non-working hours without requiring cook intervention (see [Planning in real time](/docs/explanation/planning-in-real-time/)).
- **An active range represents operational uncertainty.** The declaration `~{40-50min}` represents how long the chicken takes to roast. The schedule always defaults to the longest bound (50 minutes) so that service is never delayed. Passive elasticity settings (`rests`) do not apply to active timers.

:::note
Deprecated fields of the compiled recipe (`steps[].timings`, `steps[].backgroundTasks`, and `metrics`) continue to evaluate ranges as their average value until version 2.0.0. Consume the modern `schedule` blocks instead.
:::

## Active vs passive

The Gram compiler builds a complete execution timeline (similar to a Gantt chart) for each recipe. To achieve realistic scheduling, it distinguishes hands-on kitchen work from autonomous background tasks.

:::tip[💡 The Golden Rule: Does this step block YOU from starting the next step?]

| Cook Status | Timer Type | Syntax | Culinary Examples |
| :--- | :--- | :--- | :--- |
| **YES** (Exclusive manual attention required) | **Active** | `~` | *Whisking by hand, stirring risotto, plating* |
| **NO** (Equipment or time does the work) | **Passive** | `~_` | *Oven baking, fermentation, simmering, chilling* |

:::

### Active (default)
By default, a `~timer` is active. It requires direct hands-on involvement: the step is **blocking** and demands undivided attention before moving on to subsequent operations.

```gram
Whisk the @heavy cream{} continuously for ~{5min}.
```
> ⏱️ **Result:** Adds 5 minutes to **active time**.

### Passive (`_`)
Add the `_` modifier to designate a passive `~timer`. This represents a **background task**. You initiate the timer (e.g. putting a dish into the oven) and can immediately proceed with subsequent steps.

```gram
Bake in the #oven for ~_{45min}.

Meanwhile, prepare the glaze...
```
> ⏱️ **Result:** Adds 0 minutes to active time, but extends **idle / passive duration** to ensure these 45 minutes elapse before removing the dish.

### Sequential passive timers (named tracks)
By default, passive timers run concurrently with the rest of the recipe. However, certain background operations sharing equipment cannot physically overlap (e.g. blind-baking a crust for 10 minutes, then lowering the heat and continuing baking for 30 minutes in the same oven).

To enforce **sequential** execution of passive timers, assign them the **same track name**:

```gram
Bake in the #oven at 240°C for ~_baking{10min}.

Lower the heat to 180°C and bake for ~_baking{30min}.
```

> ⏱️ **Result:** Because both timers share the track name `baking`, Gram places them on the same background track. The 30-minute timer will only start *after* the 10-minute timer completes. Idle waiting time increases by 40 minutes, while active hands-on time remains zero.

## How time is calculated

Behind the scenes, Gram tracks four distinct time metrics to establish realistic schedules:

:::note[⏱️ The 4 time metrics]
1. **Preparation time** (mise en place): Time spent gathering and preparing raw ingredients and cookware (fetching, weighing, peeling, chopping).
2. **Active time**: Cumulative hands-on duration spent executing culinary steps.
3. **Passive time**: Autonomous baking, resting, fermentation, or idle waiting time.
4. **Total time**: Preparation time + active time + passive time. Represents the overall recipe span from initial mise en place to plating.
:::

### Cheat sheet: what adds time?

Here is how the compiler converts syntax elements into working minutes:

| Syntax / Scenario | Adds to preparation time | Adds to active time | Adds to passive time |
| :--- | :--- | :--- | :--- |
| **New ingredient** (`@flour`) | **+ 1 min** (to fetch) | - | - |
| **Intermediate** (`&dough`) | **+ 1 min** (to weigh where consumed) | - | - |
| **Prep shorthand** (`@onion(peeled)`) | **+ 2 min** | - | - |
| **Cookware** (`#pan`) | **+ 1 min** (to fetch) | - | - |
| **Active timer** (`~{10min}`) | - | **+ 10 min** | - |
| **Passive timer** (`~_{1h}`) | - | - | **+ 1 hour** (background) |
| **Step without any timer** | - | **+ 2 min** (default fallback) | - |

### When the mise en place happens
<Since v="1.4.0" />

Each section has its own mise en place (gathering and preparing ingredients and cookware). Gram supports three layout strategies without requiring any changes to the recipe source text:

- **By section** (`perSection`, default): mise en place is scheduled immediately prior to that section. An ingredient needed two days later is not fetched prematurely, and preparation can occur during passive waiting times of earlier steps (masked time).
- **All at the start** (`upfront`): all prep tasks are grouped at the beginning before active cooking starts. Except for intermediate preparations, which cannot be weighed before they are produced.
- **By working day** (`perSession`): for multi-day recipes, preparation tasks for each day are grouped at the start of that day's session. Days are determined by section anchors **in days** (`~{-1d}`, `~{-2d}`). Recipes without day anchors execute in a single working day session, identical to `upfront`.

Two considerations for multi-day recipes:
- **A long passive timer is not an anchor.** A `~_{48h}` passive duration shifts the timeline two days earlier, but only an explicit section anchor formally opens a separate working day (e.g. `## Cream ~{-2d}`).
- **An anchor in hours never opens a day.** An anchor such as `~{-18h}` or `~{-36h}` represents an explicit deadline within that section's day, not an independent daily session. To schedule a previous working day, use `~{-1d}` (see [Days and hours](#days-and-hours)).

Strategy selection happens at render time: the Playground features a dropdown selector, VS Code provides the `gram.miseEnPlace` setting, the CLI exposes the `--mise-en-place` flag, and the renderer accepts `miseEnPlace`. This setting influences **total duration** and **idle time**, as well as block positioning on the Gantt chart, while keeping active preparation and hands-on cooking times invariant.

An intermediate preparation (`&dough`) is weighed in the section that consumes it and never before it is produced: even in `upfront` mode, it is scheduled as a deferred block immediately before the consuming section.

### Smart dependency tracking (ALAP)
Gram natively implements an **As Late As Possible (ALAP)** scheduling algorithm. If a dough requires `~_{1h}` passive fermentation in the background and a subsequent step depends on it, the compiler plans its kneading at the latest possible moment: fermentation finishes *exactly* when the next step begins, preventing dough from sitting over-proofed on the counter.

For a deeper architectural exploration, see the [ALAP scheduling deep dive](/docs/explanation/alap-scheduling/).

## Section retro-planning

Adding a `~{...}` annotation to a `## Section` header defines an anticipation deadline. This tells the compiler when the section must conclude relative to the final step where it is consumed.

**This acts as a temporal anchor.** An annotation like `~{-2d}` instructs the compiler to complete this section **2 full days before** it is needed in subsequent steps.

To ensure positive relative timestamps starting at `0`, the compiler normalizes the timeline: this anticipated section becomes the new start point (Time 0), and all subsequent operations are shifted proportionally. Its mise en place moves accordingly, scheduled immediately before the section, two days prior to service.

```gram
## Puff pastry ~{-2d}
```

The puff pastry must be completed **2 days** before final assembly.

### Days and hours
<Since v="1.4.0" />

The chosen unit defines the anchor's semantics:

- **An anchor in days** (`~{-1d}`, `~{-2d}`) opens a distinct working day (day before, two days before), anchoring the "by working day" strategy and day labels (D-1, D-2).
- **An anchor in hours or minutes** (`~{-18h}`, `~{-90min}`) specifies a precise deadline within that section's scheduled day, without opening a new working day.

Working days are designed to fit within a 24-hour span: if a long passive duration pushes a day's work out of its window (such as a `~{-1d}` dough fermenting for 50 hours), the compiler emits `SESSION_OVERFLOW` and recommends anchoring the section further back.

### Strict syntax

Section header retro-planning annotations require a **strictly negative** signed number followed by a valid unit:

- A **required** leading `-` sign.
- A non-zero numeric value.
- A canonical unit: `d` (days), `h` (hours), or `min` (minutes), or recognized localized aliases.

```gram
## Puff pastry ~{-2d}     <!-- 2 days before -->
## Ganache ~{-30min}      <!-- 30 minutes before -->
```

Free prose (`~{the day before}`), positive values (`~{2h}`), and zero values (`~{0h}`) are invalid. Existing recipes using legacy formats still compile for backward compatibility, but produce compiler warnings.

Units resolve through the multi-language time dictionary used by `~timer`: `j`, `jour`, and `jours` are recognized aliases for `d`.

See also: [Retro-planning (Scheduling)](/docs/reference/syntax/document-structure#retro-planning-scheduling) in the document structure reference.

## Error handling

The compiler validates `~timer` declarations and section retro-planning annotations, emitting typed warnings for malformed data:

- **Missing Unit** (`~timer`): `~{30}` without units triggers `MISSING_UNIT`.
- **Invalid Unit** (`~timer`): Unrecognized units (e.g. `~{30 lightyears}`) trigger `INVALID_UNIT`.
- **Missing Unit** (section retro-planning): `~{-2}`, free text, positive (`~{2h}`), or zero values (`~{0h}`) trigger `MISSING_UNIT`.
- **Invalid Unit** (section retro-planning): Unrecognized units trigger `INVALID_UNIT`.
- **Time Paradox**: Anchors conflicting with dependency order (e.g. an ingredient anchored at `-10 min` needed by a section anchored at `-1 h`) trigger `TIME_PARADOX`.
- **Track Contention**: Concurrent passive timers delayed on the same named track trigger `TRACK_CONTENTION`.
- **Session Overflow** *(Since 1.4.0)*: Passive durations pushing working day tasks beyond the 24-hour window trigger `SESSION_OVERFLOW`.
- **Duration Out Of Range**: Durations exceeding 1,000 years are capped and trigger `DURATION_OUT_OF_RANGE`.

Warnings are non-blocking by default, but can be enforced as errors via `gram check --strict`.
