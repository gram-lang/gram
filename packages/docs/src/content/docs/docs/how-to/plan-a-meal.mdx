You want to serve a country bread on Sunday at 1 p.m. The dough requires an overnight rise, you are only available to cook between 8 a.m. and 10 p.m., and you would rather avoid kneading at 4 a.m. This guide walks you through turning a recipe into a timestamped production run sheet, and exporting your schedule directly to your calendar.

<Steps>

1. ### Define passive durations as ranges

   A fixed passive duration (`~_{8h}`) will never shift. In contrast, a passive timer defined as a range (`~_{8-16h}`) provides temporal slack: Gram leverages this margin to push active work outside your overnight unavailability window.

   ```gram
   ---
   title: Country bread
   ---

   ## Dough ->&dough

   [Mix] Mix @flour{500g} with @water{350ml} and @salt{10g}, then knead ~{20min}.

   [Rise] Let it rise ~_{8-16h}.

   ## Bake

   [Bake] Shape &dough{850g} and bake at ^{230C} for ~{30min}.
   ```

   `~_{8-16h}` specifies that the fermentation is ready after 8 hours, yet remains viable for up to 16 hours. See [Exact times and ranges](/docs/reference/syntax/times/#exact-times-and-ranges).

2. ### Specify target serving time and cooking availability

   ```bash
   gram plan bread.gram --serve "2026-10-11 13:00" --tz Europe/Paris --available 08:00-22:00
   ```

   `--serve` specifies the target local date and time, `--tz` sets the reference IANA time zone, and `--available` establishes your default daily activity window. Without `--available`, Gram assumes that active cooking tasks can occur at any hour.

   If you routinely cook in the same location, set your default time zone once instead of passing `--tz` every time: `gram config set timezone Europe/Paris` (stored in `.gram/config.yaml` or in your global user configuration). Otherwise, Gram falls back to your host machine's system time zone, which may produce unintended shifts on remote servers or when planning across time zones.

3. ### Analyze the generated run sheet

   ```text
   Production sheet — Country bread
   Served Sunday, October 11 at 13:00

   Saturday, October 10 · D-1
     around 21:35      Mise en place — Dough (3m)
                       Ingredients lookup (base) (3 × 1m)
     around 21:40      Dough — Mix (20m)
                       Mix flour (500 g) with water (350 ml) and salt (10 g), then knead ⏲️ 20 min.
     around 22:00      Rise — Dough (14h 30m, until around Sun 12:30)
                       Let it rise ⏳ 8-16 h (passive).
                       ! Wait stretched from 8h to 14h 30m to stay out of your unavailable hours

   Sunday, October 11 · Day D
     around 12:30      Mise en place — Bake (1m)
                       Ingredients lookup (base) (1 × 1m)
     around 12:30      Bake — Bake (30m)
                       Shape dough (850 g) and bake at 🔥230 °C for ⏲️ 30 min.

   To fix
     - The work of Day D falls on Saturday, October 10 instead of Sunday, October 11.
   ```

   Without availability constraints, an 8-hour rise would have scheduled kneading at 04:10 on Sunday morning. Gram automatically extended the rise to 14 h 30 min so that kneading finishes at 22:00 on Saturday night, right before your unavailable window. The adjustment is explicitly reported directly under the passive task. Timestamps are rounded to the nearest five minutes ("around") to facilitate kitchen execution.

   The "To fix" section (`SESSION_DAY_MISMATCH`) serves as an informative notice rather than a blocking error: active work extends to Saturday even though the recipe did not declare a multi-day schedule. For an overnight rise, this behavior is expected and can be safely ignored. If you prefer to formalize this split, anchor the upstream section (`## Dough ~{-1d}`): Saturday becomes day D-1 and the diagnostic disappears. Note that an anchor establishes a strict deadline (the dough must be ready on Saturday at the same time as service), which disables elastic expansion of the rise. See [Days and hours](/docs/reference/syntax/times/#days-and-hours).

4. ### Customize availability windows and exceptions

   Availability can vary across days of the week or specific dates. You can repeat `--available`:

   ```bash
   gram plan bread.gram --serve "2026-10-11 13:00" \
     --available 08:00-22:00 \
     --available sat=09:00-23:00 \
     --available 2026-10-09=none
   ```

   `sat=...` applies to a weekday (`mon` … `sun`), while `2026-10-09=none` declares complete unavailability on that calendar date. Multiple time slots can be grouped under a single key, separated by commas (`sat=08:00-09:00,18:00-22:00`). If a constraint cannot be met (for instance with a fixed passive timer or an overly narrow range), the run sheet lists the diagnostics under "To fix" along with actionable guidance. See [Diagnostics and unresolved constraints](/docs/explanation/planning-in-real-time/#diagnostics-and-unresolved-constraints).

5. ### Export to calendar (.ics)

   ```bash
   gram plan bread.gram --serve "2026-10-11 13:00" --available 08:00-22:00 --ics bread.ics
   ```

   The generated iCalendar file creates an event for each task and sets a reminder 5 minutes before every active task. Events are stored in UTC (ISO 8601): your calendar application automatically displays them in your local time zone.

6. ### Annotate the recipe with real-time schedule

   While the production sheet is strictly chronological, the recipe preserves its section-based structure. To view the recipe annotated with step-by-step timestamps, pass the same planning flags to the display and export commands:

   ```bash
   gram view bread.gram --serve "2026-10-11 13:00" --available 08:00-22:00
   gram export bread.gram --format md --serve "2026-10-11 13:00" --available 08:00-22:00
   ```

   The annotated view displays the target time beside each step, working day changes, passive duration adjustments, and a header summary with the target serving time and any diagnostics. You can add `--with-sheet` to `gram export` or `gram print` to append the run sheet to the recipe in a single unified document. In the playground, the preview and Markdown tabs reflect these annotations as soon as a serving time is configured in "Plan".

7. ### Select output formats

   Use `--format md` for Markdown (ready to paste into note-taking apps), `--format html` for a standalone snippet, and `--format json` to inspect the complete plan and run sheet as structured data. Run sheet labels automatically reflect your project's configured language (`language` in `.gram/config.yaml`).

</Steps>

## In the playground

Switch to the Gantt chart or the "Production sheet" view, open the "Plan" panel, and enter your target serving time, time zone, and availability windows. The Gantt chart instantly projects onto the real calendar scale, shading unavailable periods and highlighting passive durations that underwent adjustment.

## Programmatic usage

```typescript
import { compile } from '@gram-lang/kitchen';
import { project, runSheet } from '@gram-lang/scheduler';
import { runSheetToText } from '@gram-lang/renderer';

const compiled = compile(ast);
const plan = project([{ graph: compiled.tasks, title: compiled.title ?? undefined }], {
  serveAt: '2026-10-11T13:00',
  timeZone: 'Europe/Paris',
  availability: { daily: [{ start: '08:00', end: '22:00' }] },
});

console.log(runSheetToText(runSheet(plan), compiled));
```
