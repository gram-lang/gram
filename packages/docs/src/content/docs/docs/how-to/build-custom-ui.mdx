---
title: "How to build a custom UI (consuming JSON)"
description: "Consume Gram's compiled JSON output directly in React, Vue, or Svelte to build a fully custom recipe UI."
---

If you are building a modern web application (e.g., using React, Vue, Svelte, or Next.js), you should consume Gram's compiled **JSON data** directly and map it to your own user interface (UI) components.

While the raw output of the parser is an Abstract Syntax Tree (AST), the `@gram-lang/kitchen` and `@gram-lang/analyzer` packages transform this AST into a highly structured, render-ready JSON object. This guide shows you how to programmatically extract this JSON data and understand its architecture so you can build anything you want.

1. ### Getting the JSON data
   
   Gram is designed to run in any JavaScript runtime (Node.js, Edge environments, or directly inside the browser). To obtain the fully enriched JSON representation of a recipe, compose its three core packages:
   
   ```typescript
   import { getAST } from '@gram-lang/parser';
   import { compile } from '@gram-lang/kitchen';
   import { analyze } from '@gram-lang/analyzer';
   
   function getRecipeData(sourceCode: string) {
     // 1. Parse text into an abstract syntax tree
     const ast = getAST(sourceCode);
     
     // 2. Compile into structured sections and compute the default schedule
     const compiled = compile(ast);
   
     // 3. Enrich with culinary mathematics (physical masses, yields, nutrition)
     const analyzed = analyze(compiled, myDatabase);
   
     return analyzed.result;
   }
   ```
   
   :::tip[Node.js runtime shortcut]
   If you are exclusively running in a Node.js environment (a CLI tool, a Next.js server route, etc.), `@gram-lang/cli` exports a `runPipeline(filePath, options?)` helper that orchestrates the three stages above and handles file reading for you:
   
   ```typescript
   import { runPipeline, GramCLIError } from '@gram-lang/cli';
   
   try {
     const { compiled, analyzed } = await runPipeline('recipe.gram', { db: myDatabase });
     return analyzed ? analyzed.result : compiled;
   } catch (err) {
     if (err instanceof GramCLIError) {
       console.error(err.message); // e.g. "File not found: recipe.gram"
     }
     throw err;
   }
   ```
   
   Omit `db` to skip the physical analysis stage entirely (`analyzed` will be `null`). See [`@gram-lang/cli`'s API reference](/docs/reference/api/#optional-node-only-shortcut-gram-langcli) for the full option list (scaling factor, baker's percentages, etc.).
   :::
   
   :::note
   See the [API Reference](/docs/reference/api/) for the complete signatures of `getAST`, `compile`, and `analyze`, plus everything else the pipeline exposes (scaling, semantic diffing, warning diagnostics, i18n).
   :::

2. ### Understanding the JSON structure
   
   The returned JSON object encapsulates the entire recipe in a deterministic structure. It provides everything you need to build your UI:
   
   - `title` *(string)*: The recipe name (defined by the `# Title` heading).
   - `meta` *(object)*: Key-value metadata pairs (e.g. `author`, `portions`, `yield`).
   - `shopping_list` *(array)*: An aggregated list of all ingredients across all sections, ready for procurement.
   - `sections` *(array)*: The culinary instructions broken down by standalone section.
   - `metrics` *(object)*: Global metrics (`preparationTime` and `activeTime` in minutes, plus mass and nutrition when passed through the analyzer).
   - `miseEnPlace` *(array)*: Detailed operational items and prep durations for each section requiring mise en place.
   - `tasks` *(object)*: The neutral task graph containing durations and dependencies, serving as the foundation for all scheduling passes.
   - `schedule` *(object)*: The default theoretical schedule laid out from `tasks`, including `totalTime`, `idleTime`, scheduled `blocks`, and working-day `sessions`.
   - `generator` *(string)*: Which version of the compiler generated this document.
   
   To ensure forward compatibility when minor versions introduce new fields or block `kind` values, gracefully ignore unrecognized properties in your UI.
   
   #### Inside a section
   
   Each entry in the `sections` array has its own `ingredients`, `cookware`, and `steps`.
   
   ```json
   {
     "title": "Dough",
     "ingredients": [ ... ],
     "cookware": [ ... ],
     "steps": [
       {
         "type": "step",
         "action": "Mix",
         "content": [
           "The ",
           {
             "id": "flour",
             "_usageId": "1",
             "qty": 500,
             "unit": "g",
             "normalizedMass": 500
           },
           " and ",
           {
             "id": "water",
             "_usageId": "2",
             "qty": 350,
             "unit": "ml"
           },
           "."
         ]
       }
     ]
   }
   ```
   
   A step no longer carries its own hardcoded timestamps. Where it sits in time depends on the selected mise en place strategy, so timing blocks reside within `schedule` (see "Drawing the timeline" below).

3. ### Rendering logic
   
   Because Gram's JSON payload is highly consistent, generating a UI is a straightforward matter of iterating over arrays with standard frontend framework patterns.
   
   #### Example: rendering steps in React
   
   Here is a conceptual example showing how to render the `steps` array and its inline tokens in React:
   
   ```tsx
   function RecipeStep({ step }) {
     // If it's a comment node
     if (step.type === 'comment') {
       return <p className="text-gray-500 italic">{step.value}</p>;
     }
   
     // If it's a standard instruction step
     if (step.type === 'step') {
       return (
         <li>
           {step.action && <strong>[{step.action}] </strong>}
           {step.content.map((token, i) => (
             <StepToken key={i} token={token} />
           ))}
         </li>
       );
     }
   }
   
   // A polymorphic component to render inline tokens
   function StepToken({ token, cookwareRegistry }) {
     // 1. Strings represent raw prose
     if (typeof token === 'string') {
       return <span>{token}</span>;
     }
   
     // 2. Ingredients and Cookware are optimized objects without a 'type' field, identified by 'id'.
     // We differentiate cookware by checking if the identifier exists in our cookware registry.
     if (!token.type && token.id) {
       const isCookware = !!cookwareRegistry[token.id];
       
       if (isCookware) {
         return <span className="text-blue-600 font-bold">{token.id}</span>;
       } else {
         return <span className="text-green-600 font-bold">{token.id} ({token.qty}{token.unit})</span>;
       }
     }
   
     // 3. Other tokens (timers, temperatures) have explicit 'type' fields
     switch (token.type) {
       case 'timer':
         return <span className="bg-yellow-100 px-1 rounded">{token.quantity?.value}{token.unit}</span>;
       case 'temperature':
         // Unit is already normalized to °C/°F
         return <span className="text-red-600">{token.quantity?.value}{token.unit}</span>;
       default:
         return null;
     }
   }
   ```
   
   By mapping the `type` property to your own components, you have **total control** over design tokens, interactivity, and accessibility across your application.

4. ### Drawing the timeline
   
   <Since v="1.4.0" />
   
   To draw a Gantt chart or a visual schedule, read the timeline blocks. `recipe.schedule` provides the default schedule; any alternative variant can be laid out from `recipe.tasks` via the `layout()` function without recompiling the recipe. Every time offset is in minutes relative to `t = 0` and already accounts for the required mise en place:
   
   ```typescript
   import { layout } from '@gram-lang/scheduler'; // or scheduleFor() from '@gram-lang/kitchen'

   // miseEnPlace: 'perSection' (each section's preparation right before it, default),
   //   'upfront' (all preparation grouped at the very start), or 'perSession' (preparation
   //   grouped at the beginning of each working day).
   // rests: elasticity applied to passive timers defined as ranges
   //   (e.g. fermentation, resting, slow cooking): 'shortest' (default), 'balanced', or 'longest'.
   const { schedule } = layout(recipe.tasks, { miseEnPlace: chosenMode, rests: chosenRests });
   // For the default choice, recipe.schedule contains this precomputed layout.
   
   for (const block of schedule.blocks) {
     if (block.kind === 'prep') {
       // A section's mise en place: recipe.miseEnPlace details the associated operations
       const prep = recipe.miseEnPlace.find((m) => m.section === block.section);
       draw('Mise en place', block.start, block.end, prep?.items);
     } else {
       // 'step' (active cooking) or 'passive' (passive timer):
       // block.step is the index in sections[block.section].steps
       const step = recipe.sections[block.section].steps[block.step];
       const label = block.kind === 'passive' ? (block.track ?? 'Passive timer') : step.action;
       draw(label, block.start, block.end);
     }
   }
   ```
   
   Let your users choose their preferred strategy: total duration and idle waiting time vary across modes (`schedule.totalTime`, `schedule.idleTime`), while active preparation time remains constant (`schedule.preparationTime`). The Gram renderer, Playground, VS Code extension, and CLI all provide this strategy selector.
   
   To project the production onto a real-world calendar instead (with concrete dates, wall-clock times, and passive durations stretched to honor overnight non-working hours), pass the same `tasks` to `project()` with a target serving time, a time zone, and kitchen availability. Each block carries `start` and `end` as absolute UTC timestamps alongside `startLocal` and `endLocal` formatted in the local time zone. For details, see [Plan a meal](/docs/how-to/plan-a-meal/) and the [scheduler API reference](/docs/reference/api/scheduler/).
   
   :::caution[Deprecated fields]
   Older code written prior to version 1.4.0 may still read `step.timings`, `step.backgroundTasks`, or `metrics.totalTime`. While retained for backward compatibility until version 2.0.0, these fields are deprecated: consume `schedule` instead. See [Deprecated features](/docs/how-to/deprecations) and the [Kitchen API reference](/docs/reference/api/kitchen).
   :::
</Steps>
