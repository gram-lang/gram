A recipe describes its own timing: tasks, how long they last, and what dependencies they wait for. That is enough to calculate an overall metric—such as "this recipe takes 17 hours, 50 minutes of it in active work". It is not enough to say **when to start**. For that, Gram needs three inputs that only you know: when you serve, in which time zone, and when you can actually cook.

Provide those three parameters, and Gram positions each task along a backward calendar schedule from the serving time, organizing work days, active kitchen visits, and background resting intervals. The [work plan](/docs/how-to/plan-a-meal/) provides the operational presentation of this data.

## Inputs

| Parameter | Example | Description |
|---|---|---|
| **Serving time** | `2026-10-11 13:00` | Target local date and time, expressed in the time zone below |
| **Time zone** | `Europe/Paris` | An IANA zone: determines clock readings and daylight saving adjustments. The CLI resolves it in order: `--tz`, the project (or global) `timezone` setting, then the host machine's time zone |
| **Availability** | `08:00-22:00`, `fri=18:00-22:00`, `2026-10-09=none` | When you can work: a default daily range, plus exceptions by day of the week or by calendar date |

Availability is structured as an object: a default daily range (`daily`), exceptions by day of the week (`weekdays`), and exceptions by calendar date (`dates`). A date exception always overrides a weekday rule, which in turn overrides the default daily range. An empty list indicates complete unavailability on that day. A range that ends before it starts spans across midnight continuously (e.g. `22:00-02:00`).

:::note[Absolute determinism]
Gram never queries the system clock to compute a schedule. With the same recipe, serving time, time zone, and availability, the resulting plan is byte-for-byte identical across all environments.
:::

## How the plan is made

The recipe's theoretical timeline (see [Mise en place and planning](/docs/explanation/mise-en-place-and-planning/)) is first anchored so that it completes at the serving time. Gram then examines the constraints of **your hands-on work** (active tasks and mise en place):

<Steps>
1. **Grouping uninterrupted stretches**  
   Tasks that cannot be interrupted are grouped into a continuous block. For example, a preparation followed immediately by the step it prepares, with no wait between them, forms a single indivisible block: Gram cannot assume you can pause a kneading step halfway through to go to sleep.

2. **Validating compatible stretches**  
   Any continuous stretch that fits entirely within your availability windows remains unchanged.

3. **Adjusting conflicting stretches**  
   Any stretch that overlaps with an unavailable period is shifted by adjusting the **nearest flexible wait (defined with a range) downstream**:
   - **lengthening** the wait moves preceding work earlier (e.g. to the evening before);
   - **shortening** the wait shifts preceding work later (e.g. to the next morning).

   Gram favors the direction preferred by your wait strategy (shortest duration by default, hence shortening first), and selects the smaller shift when both are equal. It never exceeds the bounds of the range and never alters a fixed-duration wait.

4. **Propagation and traceability**  
   Each adjustment cascades to all tasks scheduled before that wait. The plan explicitly logs every change: which wait was adjusted, the initial and updated duration, and the reason for the change.
</Steps>

A wait assigned to a named track (`~_oven{40min}`) is only stretched if that track remains unoccupied throughout the extended duration. The scheduler recomputes the entire timeline on every adjustment: dependencies and track allocations are verified on the concrete layout rather than guessed.

### Concrete example

```gram
## Dough ->&dough

[Knead] Knead @flour{500g} with @water{350ml}, ~{20min}.

[Rise] Let it rise ~_{8-16h}.

## Bake

[Bake] Shape &dough{850g} and bake for ~{30min}.
```

Served on Sunday at 13:00, with `08:00-22:00` daily availability, an 8-hour rise would place the kneading at 04:10. Gram automatically stretches the rise to 14 h 30 so that the kneading finishes at 22:00 on Saturday evening:

```text
SAT 10   ▮ 21:40 – 22:00 Dough
         ┆ Dough : Rise 14h 30m (8h to 16h)
SUN 11   ▮ 12:30 – 13:00 Bake
         ★ 13:00         Serve

SATURDAY, OCTOBER 10  21:40 → 22:00
  ! Dough : Rise extended to 14h 30m (planned 8h to 16h) so the work falls within your availability.
  Possible from 20:10.
```

If the rise were exact (`~_{8h}`), or if the range was too narrow to absorb the offset (`~_{8-10h}`), no adjustment could be made: the scheduler leaves the kneading at 04:10 and logs the diagnostic.

## Diagnostics and unresolved constraints

Gram never conceals a scheduling conflict it cannot resolve. Any remaining issue is reported alongside the plan:

| Diagnostic | Meaning | Recommended action |
|---|---|---|
| `ACTIVE_OUTSIDE_AVAILABILITY` | Active hands-on work falls during unavailable hours, and no wait can move it (fixed wait, insufficient range, or no wait downstream). | Widen your availability windows or provide a flexible wait range. |
| `ACTIVE_BLOCK_EXCEEDS_AVAILABILITY` | An uninterrupted block of hands-on work is longer than your longest continuous availability window. | Widen your availability window (no wait adjustment can split this block). |
| `DAY_MISMATCH` | A working day falls on a different calendar day than intended (work tagged with `~{-1d}` landing two days prior). | Anchor the section explicitly or adjust intermediate waits. |
| `START_IN_PAST` | The first task should have started before the current planning time. | Set a later serving time or shorten waits. |
| `MULTI_RECIPE_UNSUPPORTED` | Multiple recipes were supplied; only the first was planned. | Plan recipes individually. |

:::note[Planning diagnostics vs Compiler warnings]
These diagnostics are specific to calendar projection: they depend directly on **your** availability constraints rather than recipe defects. Compiler warnings inherent to the recipe code itself (such as `DAY_OVERFLOW`, when an excessive wait pushes a working day out of its 24-hour day) are documented in [Times and durations](/docs/reference/syntax/times/#error-handling).
:::

## Time zones and daylight saving

Calculations take place in absolute minutes along a continuous timeline; conversion to local wall-clock time occurs only during final output rendering. A 24-hour wait (a dough in the fridge, say) spanning the autumn daylight saving transition lasts 24 true hours: if it begins at 13:30 on the clock the day before, it ends at 12:30 local time. Non-existent local times (e.g. 02:30 during the spring forward transition) are shifted to the next valid time; repeated times in autumn resolve to the first occurrence.

## The work plan

Calendar projection produces a comprehensive data model: exact timestamps for each block, adjusted passive rests, non-working intervals, and diagnostics for unresolved constraints. The [`runSheet()`](/docs/explanation/engine/scheduler/#from-the-schedule-to-the-work-plan) function organizes this data into work days, **active kitchen visits**, and **background resting threads** (proofing, chilling, resting), while calculating the scheduling margin available for each intervention.

The **work plan** is the operational view built on top of this model. For each day, it outlines required kitchen presence, equipment and ingredients to take out, actionable steps to execute alongside recipe sections, and unattended processes that continue in the background. To reflect culinary practice, displayed times are rounded to the nearest five minutes (while internal engine calculations remain accurate to the minute). Rest adjustments are highlighted at the top of the relevant day, and unresolved constraints are grouped at the top of the document. These presentation rules (grouping tasks into a single visit across rests under one hour, displaying margins starting at 15 minutes) belong to the rendering layer rather than rigid engine constraints.

The plan can be generated as plain text, Markdown, standalone HTML, a print-ready document (one day per page with check boxes), or exported to an iCalendar file (`.ics`). The `--with-sheet` option appends it directly to the recipe in a single document. While the recipe describes **how** to cook, the work plan specifies **when** to take action.

Without a target serving time, this same data is displayed as a relative countdown (`D-2`, `D-1`, `Day D`) with estimated durations per day (e.g. "about 55 min") and the earliest achievable serving time. Scheduling margins and rest adjustments are calculated only when real calendar availability is provided.

See [Plan a meal](/docs/how-to/plan-a-meal/) for an end-to-end practical guide.

## Available integrations

| Tool | Usage |
|---|---|
| CLI | `gram plan recipe.gram --serve "2026-10-11 13:00" --available 08:00-22:00` (optional `--tz` if set in config); `--find` to look for a serving time |
| Playground | The "Work plan" view and the "Plan" panel, with "When to serve?" |
| VS Code | `Gram: Work Plan`, in days before the service |
| `@gram-lang/scheduler` | `project()`, `runSheet()`, `findServeTimes()` and `earliestServe()` (see the [scheduler API reference](/docs/reference/api/scheduler/)) |
| `@gram-lang/renderer` | `runSheetToText`, `runSheetToMarkdown`, `runSheetToHTML`, `runSheetToPrintHTML`, and associated modular helpers (`passageKit`, `sectionProgram`) |

## Current limitations

- **Single recipe scheduling**: planning a complete menu (synchronizing starter, main, and dessert for the same service while sharing a single cook and oven) will be supported in a future release; the API already accepts a list of recipes, and reports `MULTI_RECIPE_UNSUPPORTED` for more than one.
- **No live state tracking**: the schedule is purely deterministic and maintains no persistent live runtime state. If a visit is delayed, simply run `gram plan` again to recalculate viable slots from the new time.
- **Shared resources**: equipment (oven preheating time, refrigerator space) does not yet act as globally pooled resources beyond explicit named tracks.
- **Heuristic approach**: the scheduling algorithm is greedy and deterministic (designed to be explainable and predictable rather than optimal in a mathematical programming sense): it resolves conflicts starting from the latest event and works backward in time.
