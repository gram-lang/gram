Voici les structures JSON qui transitent entre les étapes du pipeline, ainsi que le schéma YAML de la base de données d'ingrédients. Cette page vient en complément des références d'API : elle illustre la forme concrète des données manipulées par les fonctions du moteur Gram.

## 1. L'AST (`@gram-lang/parser`)

Le parseur transforme le code source de la recette en un Arbre Syntaxique Abstrait :

<Tabs>
  <TabItem label="Source .gram">
```gram
---
title: 'Crêpes'
---

## Pâte

Mélanger @farine{200g} et @lait{200ml}.
```
  </TabItem>
  <TabItem label="RecipeAST (JSON)">

`getAST()` retourne cette structure. Les décalages d'octets (`loc`) sont omis ci-dessus pour la lisibilité — chaque nœud, hormis `RecipeAST` lui-même, en possède un. Consultez la [référence du parseur](/fr/docs/reference/api/parser) pour l'inventaire complet des interfaces de nœuds et l'énumération `ASTNodeType`.

:::note[Champs de synchronisation dépréciés]
<Since type="deprecated" v="1.4.0" /> Les anciens champs `timings` et `backgroundTasks` par étape, ainsi que `metrics.totalTime`, `metrics.idleTime` et les ventilations temporelles de `metrics` sont dépréciés : ils sont maintenus jusqu'à la version 2.0.0, mais ont été omis de l'exemple ci-dessus par souci de clarté. La [référence de l'API Kitchen](/fr/docs/reference/api/kitchen) documente chaque champ et ses remplaçants.
:::

Remarquez le vocabulaire `StepToken` généré par le compilateur au sein de `content` : le texte narratif pur est une simple `string` ; les ingrédients, le matériel et les références partagent la forme `Usage` (sans champ `type`, identifiés par la présence d'un `id`) ; les minuteurs, températures, commentaires et déclarations portent chacun un discriminant `type` explicite en minuscules. Cette distinction avec l'énumération `ASTNodeType` (en PascalCase) du parseur est délibérée : elle caractérise la charge utile *compilée*, non la syntaxe d'entrée. Consultez le guide [Créer une UI personnalisée](/fr/docs/how-to/build-custom-ui) pour un exemple d'intégration dans un framework front-end.

## 3. Recettes composées (`@gram-lang/modules`)

Lorsqu'une recette importe des sous-modules via la directive modulaire `@use`, `finalizeComposed()` transforme le `CompilationResult` standard en un `ComposedCompilationResult`. Il ajoute des métadonnées modulaires à la racine de la charge utile ainsi que sur chaque section injectée :

```json
{
  "title": "Tarte au citron",
  "modules": [
    {
      "binding": "pate",
      "uri": "/bases/pate-sablee.gram",
      "title": "Pâte Sablée",
      "meta": { "title": "Pâte Sablée" },
      "scaleFactor": 1.5,
      "mode": "inline"
    }
  ],
  "sections": [
    {
      "title": "Pâte Sablée",
      "module": {
        "binding": "pate",
        "uri": "/bases/pate-sablee.gram",
        "title": "Pâte Sablée",
        "mode": "inline"
      },
      "steps": [ "/* étapes injectées du sous-module */" ]
    },
    {
      "title": "Assemblage",
      "steps": [ "/* étapes de la recette hôte */" ]
    }
  ]
}
```

- **`modules`** : Tableau des modules importés contributeurs (`ModuleInfo`), précisant le nom de liaison local, l'URI source, le facteur d'échelle résolu et le mode d'intégration (`"inline"` ou `"stocked"`).
- **`section.module`** : Présent sur toute section issue d'un import (`ComposedSection`), garantissant la traçabilité de provenance pour les interfaces utilisateurs et les moteurs de rendu.

## 4. Base de données d'ingrédients (YAML)

La base de données transmise à `validateIngredientDatabase()` ou `analyze()` est un dictionnaire plat `Record<string, IngredientData>`, indexé par le slug de l'ingrédient. La CLI `gram` accepte et déplie également une clé racine optionnelle `ingredients:`.

<Tabs>
  <TabItem label="Format enveloppé (gram init)">
```yaml
# Avec le wrapper optionnel (généré par défaut via gram init)
ingredients:
  farine:
    name: "Farine tout usage"
    aliases: ["flour"]
    category: "Céréales"
    physical:
      density: 0.59       # g/mL — fait le pont entre unités de volume ("1 tasse") et masse en grammes
      yield: 1.0          # fraction (0, 1] — ratio net/brut après épluchage ou parage
      unit_weight: 120    # grammes par « unité » (ex. : "1 farine" si utilisé nu)
    nutrition:            # toutes les valeurs pour 100 g de produit brut
      calories: 364       # en kcal
      protein: 10.3       # en grammes
      carbs: 76.3         # en grammes
      fat: 1.0            # en grammes
      sugar: 0.3          # en grammes
      fiber: 2.7          # en grammes
      sodium: 2           # en milligrammes (mg)
```
  </TabItem>
  <TabItem label="Format plat (analyze)">
```yaml
# Forme plate directe (attendue par validateIngredientDatabase() et analyze())
farine:
  name: "Farine tout usage"
  physical:
    density: 0.59
```
  </TabItem>
</Tabs>

Les blocs `physical` et `nutrition` sont tous deux optionnels. Une entrée dépourvue de ces blocs reste valide (elle ne fournira simplement aucune conversion de masse ou macro nutritionnel, déclenchant un `missingMassIngredients` ou l'avertissement `MISSING_MACROS`). Seul le champ `name` est strictement obligatoire. Les sous-champs `nutrition.calories`, `protein`, `carbs` et `fat` sont obligatoires dès lors que la clé `nutrition` est déclarée. Les autres (`sugar`, `fiber`, `sodium`, `sat_fat`, `mono_fat`, `poly_fat`, `alcohol`) sont optionnels.

**Les unités doivent être scrupuleusement respectées** : `calories` est exprimé en kcal, `sodium` en **milligrammes (mg)**, et tous les autres nutriments en grammes (g) — l'ensemble étant rapporté à 100 g d'ingrédient brut. L'inventaire complet des nutriments gérés, leurs unités et leur ordre d'affichage proviennent de la constante canonique `NUTRIENTS` exportée par `@gram-lang/analyzer`.
