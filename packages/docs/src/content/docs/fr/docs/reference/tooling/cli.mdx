Le CLI officiel de Gram (`@gram-lang/cli`) est l'outil de référence pour valider, compiler et gérer vos collections de recettes en local. Il fait office de passerelle entre vos fichiers `.gram` et le reste de votre stack technique (SSG, Next.js, applications mobiles, etc.).

## Installation

import { Steps, LinkCard, CardGrid } from '@astrojs/starlight/components';

<CodeTabs>
  ```bash title="npm"
  npm install -g @gram-lang/cli
```
  ```bash title="bun"
  bun add -g @gram-lang/cli
```
</CodeTabs>

Le CLI fonctionne aussi bien sous Node.js (>=22, chargeant nativement les fichiers `.env` via `process.loadEnvFile`) que sous [Bun](https://bun.sh/). Aucune API spécifique à un environnement d'exécution n'est requise, les deux options étant strictement équivalentes.

<Since v="1.2.0" /> Quand une nouvelle version est publiée sur npm, `gram` affiche une courte notification une fois la commande terminée (ignorée en environnement d'intégration continue et hors terminal interactif). Exécutez `gram upgrade` pour vérifier et installer les mises à jour à la demande, ou désactivez cette notification avec `gram config set updateCheck false` — ou, pour une seule exécution, via la variable d'environnement `GRAM_NO_UPDATE_CHECK`.

## Options globales

- `--verbose` / `--debug` : utilisable avec n'importe quelle commande, affiche la pile d'appels complète en cas d'erreur au lieu du message concis.
- `--stock <specifiers>` : traite les sous-recettes indiquées comme déjà prêtes ou en stock (ignore leurs étapes de préparation sur le calendrier et les regroupe sous la forme d'un produit fini unique sur la liste de courses). Accepte une liste de chemins séparés par des virgules (`@bases/pate-sablee.gram,./sauces/bechamel.gram`).

## Commandes principales

### Gestion de projet & flux de travail développeur

#### `gram init`
Initialise un nouvel environnement Gram dans le dossier courant.
- Crée un répertoire `.gram/`.
- Génère un fichier `config.yaml` vierge (sans commentaires superflus).
- Configure de manière interactive votre langue de recette préférée (actuellement `en` ou `fr`).
- Configure de manière interactive votre fournisseur d'IA et modèle préférés.
- Génère ou met à jour un fichier `.env` pour vos clés d'API IA.
- Génère une base de données d'ingrédients de départ documentée à l'emplacement `.gram/ingredients.yaml`.
- Génère un fichier `.gitignore` pour éviter de versionner des clés sensibles.

#### `gram upgrade` <Since v="1.2.0" />
Vérifie sur le registre npm si une nouvelle version de `@gram-lang/cli` est disponible et propose de l'installer.
```bash
gram upgrade
```
- Effectue systématiquement une requête directe auprès du registre npm — indépendamment de la vérification passive en arrière-plan.
- Affiche une comparaison entre la version installée et la dernière version disponible, puis demande confirmation avant d'exécuter `npm install -g @gram-lang/cli@latest`.
- Ne produit aucune modification (en dehors du rapport d'état) si le CLI est déjà à jour.

#### `gram check [motif]`
Valide vos fichiers `.gram` afin de vérifier la syntaxe, l'intégrité structurelle et la conformité des ingrédients.
- Exécute l'analyseur syntaxique Ohm.js pour intercepter les erreurs de syntaxe.
- Exécute le compilateur Kitchen pour détecter les erreurs structurelles (ex. dépendances circulaires).
- Interroge votre base `ingredients.yaml` pour signaler les ingrédients non documentés.
- Les simples avertissements (estimations nutritionnelles, annotations incomplètes) ne font pas échouer la commande par défaut — seules les erreurs structurelles bloquantes (références introuvables, conflits de portée) déclenchent un code de sortie non nul. Spécifiez `--strict` pour traiter le moindre avertissement comme une erreur (particulièrement adapté aux pipelines d'intégration continue).
- Options : `--db <chemin>`, `--skip-db`, `--strict`.

#### `gram build [motif]`
Compile vos recettes `.gram` au format JSON final minifié.
```bash
gram build "**/*.gram" --output ./dist
gram build brioche.gram --pretty
gram build brioche.gram --scale 2 --output ./dist-double
```
- Par défaut, émet le JSON directement sur la sortie standard (`stdout`) pour faciliter l'enchaînement avec d'autres outils en ligne de commande.
- Calcule automatiquement les données nutritionnelles et la standardisation des masses physiques à partir de la base de données.
- `--scale <facteur>` intègre le facteur d'ajustement des proportions directement dans le JSON de sortie. Le mode par référence d'ingrédient (ex. `farine=300g`) n'est volontairement pas disponible ici : `build` traitant les fichiers par lots, un résultat reproductible ne doit pas dépendre de la lecture préalable d'une liste de courses spécifique. Utilisez `gram view` ou `gram scale` pour déterminer votre facteur, puis transmettez ce multiplicateur numérique à `build`.
- Lorsqu'un motif de recherche ou plusieurs fichiers sont passés en argument, les modules importés (via `@use`) par d'autres recettes du lot sont exclus par défaut, évitant ainsi que leurs ingrédients ne soient comptabilisés en double (à la fois isolément et au sein de la recette hôte). Spécifiez `--include-modules` pour les compiler malgré tout.
- Options : `--output/-o <dossier>`, `--pretty`, `--scale <facteur>`, `--db <chemin>`, `--skip-db`, `--include-modules`.

#### `gram view <fichier>`
Affiche une recette directement dans le terminal, mise en forme dans un tableau ASCII soigné.
```bash
gram view brioche.gram                      # Vue par défaut
gram view brioche.gram --scale 2            # Proportions doublées
gram view brioche.gram --scale farine=300g  # Proportions ajustées pour farine = 300g
```
- Prend en charge la pagination automatique pour les recettes longues.
- Affiche la synthèse nutritionnelle, les durées et la liste d'ingrédients à cocher.
- Les minuteurs préservent l'unité déclarée dans la source (`~{1h}` s'affiche `~1h`, `~{20s}` s'affiche `~20s`) et les durées sont harmonisées pour une lecture instantanée (`1h 5m`, `25m 5s`).
- Le temps d'attente passif apparaît dans l'en-tête de la recette, et les fractions courantes telles que `1/4 tsp` restent sous forme fractionnaire dans la liste de courses.
- Le drapeau `--scale` ajuste l'intégralité des quantités d'ingrédients (liste de courses et rappels au sein des étapes).
- Options : `--scale <facteur|réf>`, `--no-pager`, `--skip-db`, `--db`, `--bakers-math`, `--bakers-reference <id>`, `--bakers-math-only`, `--nutrition <base>`, `--mise-en-place <mode>`, `--rests <choice>`.
- `--nutrition <auto|total|per-portion|per-100g>` <Since v="1.1.0" /> choisit la base nutritionnelle affichée (par défaut `auto` : par portion quand la recette déclare `portions:`, sinon pour l'intégralité de la recette). `per-100g` calcule les valeurs pour 100 g de préparation brute assemblée — voir [Estimation nutritionnelle](/fr/docs/explanation/nutrition).
- `--mise-en-place <per-section|upfront|per-session>` <Since v="1.4.0" /> définit l'ordonnancement de la mise en place : immédiatement avant chaque section (`per-section`, par défaut), au tout début de la recette (`upfront`) ou à l'ouverture de chaque journée de travail (`per-session`). Les durées totale et passive de l'en-tête reflètent cet ordonnancement, tandis que les temps actif et de préparation restent constants. Voir [Quand se fait la mise en place](/fr/docs/reference/syntax/times#quand-se-fait-la-mise-en-place).
- `--rests <shortest|balanced|longest>` <Since v="1.4.0" /> définit la résolution des durées variables pour les minuteurs passifs (`~_{12-24h}`) : durée minimale (`shortest`, par défaut), médiane (`balanced`) ou maximale (`longest`). Les durées exactes et les minuteurs actifs ne sont pas affectés. Ajuste les mêmes durées d'en-tête que `--mise-en-place`.
- `--serve`, `--tz`, `--available` <Since v="1.4.0" /> projettent la recette sur le calendrier réel selon le moteur de rétro-planning de `gram plan` : chaque étape reçoit une heure locale précise (avec indication des changements de journée et des plages de temps passif), et l'en-tête synthétise l'heure de service ciblée ainsi que les contraintes non résolues. La durée totale affichée correspond alors à l'envergure calendaire du plan. Ces options exigent impérativement `--serve` et sont rejetées avec une erreur si `--serve` est omis.

#### `gram import <source>`
Importe une recette depuis une page web, un fichier JSON-LD local ou une vidéo / Short YouTube, et la convertit en syntaxe `.gram` à l'aide de l'IA.

```bash
gram import "https://exemple.com/recette"         # Page web avec Schema.org / JSON-LD
gram import recette.json                           # Fichier JSON / JSON-LD local
gram import "https://www.youtube.com/watch?v=…"    # Vidéo YouTube
gram import "https://www.youtube.com/shorts/…"     # YouTube Short (normalisé automatiquement)
gram import recette.json -o brioche.gram -y        # Écriture directe sans confirmation
```

**Sources prises en charge :**
- **URL de pages web** : extrait automatiquement les métadonnées de recette structurées `application/ld+json` (Schema.org `Recipe`) présentes sur la page.
- **Fichiers JSON / JSON-LD locaux** : analyse directement les schémas JSON-LD enregistrés sur votre machine.
- **Vidéos et Shorts YouTube** <Since v="1.1.0" /> : analyse directement le contenu vidéo grâce aux capacités multimodales natives de Gemini (sans dépendre de services tiers de transcription de sous-titres).

**Fonctionnement & garde-fous :**
- Traduit et met en forme la recette selon la syntaxe Gram canonique, en respectant le paramètre de configuration `language`.
- Requiert la configuration préalable d'un fournisseur d'IA (voir [Configurer l'IA](/fr/docs/how-to/configure-ai)).
- Avant d'écrire dans `--output`, la recette convertie est présentée pour relecture et validation interactive. En contexte non interactif, la relecture est ignorée avec un avertissement — spécifiez `--yes/-y` pour confirmer explicitement l'écriture.
- **Rien n'est produit si le résultat de l'import présente des incohérences majeures.** Deux contrôles stricts sont appliqués :
  - *Détection de perte de contenu* — chaque `@ingrédient` présent dans le texte source est confronté à ce que le compilateur a effectivement enregistré. Un écart signale une portion de texte éludée (souvent causée par un commentaire `//` inséré au milieu d'une phrase et masquant le reste de la ligne). Un tel fichier pourrait compiler sans avertissement tout en étant amputé d'ingrédients essentiels.
  - *Correction des erreurs critiques* — le moteur accorde deux tentatives de réparation autonome au modèle d'IA pour corriger d'éventuelles erreurs de syntaxe. Si des erreurs subsistent, elles sont consignées dans le terminal et l'écriture du fichier est annulée.

  Spécifiez `--force` pour imposer l'écriture malgré les avertissements, ou réessayez avec un `--model` aux capacités supérieures.
- `source:` et `author:` proviennent directement des données sources (ou des métadonnées de la vidéo YouTube), et sont omis s'ils sont absents — le modèle n'extrapole jamais ces champs.
- **Les ingrédients déclarés sans quantité sont comptabilisés et répertoriés par numéro de ligne.** Il ne s'agit pas d'une erreur de syntaxe — la syntaxe `@sel{}` est idiomatique pour indiquer "au goût" —, mais d'un indicateur objectif du niveau d'exhaustivité de la recette, guidant précisément vos ajustements manuels. Un ingrédient quantifié lors de sa première occurrence puis simplement rappelé ultérieurement n'est pas comptabilisé comme non dosé.
- Lorsqu'une base de données d'ingrédients est active, l'analyseur signale également les éléments non résolus (ingrédients inconnus, unités dépourvues de masse volumique). Ces éléments indiquent des lacunes dans votre base locale et ne constituent pas un échec d'importation : ils ne bloquent donc jamais l'opération.

**Spécificités de l'import vidéo YouTube :** <Since v="1.1.0" />
- **Fournisseur Google / Gemini requis** : Gemini est le seul modèle traitant nativement les vidéos YouTube à partir de leur URL. Avec tout autre fournisseur, l'importation est interrompue.
- **Consommation proportionnelle à la durée**, à raison d'environ 100 jetons d'entrée par seconde de vidéo : un Short consomme quelques milliers de jetons, 10 minutes environ 60 000 jetons, et 26 minutes environ 158 000 jetons. Les vidéos de plus de 20 minutes sont rejetées par défaut ; vous pouvez relever ce plafond via `--max-duration <minutes>`.
- **L'estimation du coût préalable requiert la variable `YOUTUBE_API_KEY`** : une clé standard de la YouTube Data API, lue exclusivement depuis les variables d'environnement (jamais stockée dans `config.yaml`). En son absence, l'importation s'exécute néanmoins, mais sans pouvoir pré-estimer la durée ni appliquer la limite de manière anticipée.
- **Attentes concernant les quantités en vidéo** : une démonstration vidéo comporte souvent moins de mesures explicites qu'un texte formel. La consigne fournie au modèle impose de laisser les accolades `{}` vides plutôt que de deviner des valeurs arbitraires. Attendez-vous donc à devoir compléter certaines proportions manuellement.
- Les champs `title:`, `author:` (nom de la chaîne) et `source:` (URL) proviennent directement des métadonnées de la plateforme et sont repris tels quels.
- Options : `--output/-o <fichier>`, `--yes/-y`, `--force`, `--max-duration <minutes>` <Since v="1.1.0" />, ainsi que les [options IA communes](#choisir-le-modèle-ia).

#### `gram shop [motif]`
Compile une liste de courses consolidée en agrégeant plusieurs recettes.
```bash
gram shop "**/*.gram"                 # Toutes les recettes
gram shop brioche.gram --scale 2      # Quantités doublées
gram shop "menus/*.gram" --scale 4    # Préparation par lots × 4
```
- Agrège les quantités de manière homogène en exploitant les masses volumiques de référence (volume → grammes lorsque la densité est connue).
- Regroupe les ingrédients selon leur champ `category` (familles culinaires : Fruits & Légumes, Produits laitiers, Céréales, etc.).
- **Consolidation par alias** : si deux recettes utilisent des désignations distinctes pour un même produit (ex. `butter` et `beurre`), elles sont fusionnées sous leur identifiant canonique commun grâce à l'index d'alias de la base de données.
- Les ingrédients dépourvus de quantité (ex. `@sel{}`) sont mentionnés à côté de leur entrée principale plutôt que relégués dans une section distincte.
- Prise en charge intégrale des micro-unités : les indications telles que `pincée`, `trait` ou `goutte` s'agrègent sans erreur.
- `--scale <facteur>` applique un multiplicateur numérique uniforme à l'ensemble des recettes (facteur global uniquement — le ciblage par référence d'ingrédient n'est pas applicable sur plusieurs fichiers).
- Lorsqu'un motif de recherche ou plusieurs fichiers sont fournis, les recettes importées (via `@use`) par d'autres fichiers du lot sont exclues par défaut pour éviter les doublons sur la liste de courses consolidée. Spécifiez `--include-modules` pour les inclure malgré tout.
- Options : `--format terminal|md|json`, `--output/-o <fichier>`, `--scale <facteur>`, `--db`, `--skip-db`, `--include-modules`.

#### `gram cook <fichier>`
Lance un guide de cuisine interactif pas à pas, directement au sein du terminal.
```bash
gram cook brioche.gram
gram cook carbonara.gram --skip-db
```
La durée totale affichée à l'écran de fin respecte les réglages `--mise-en-place` et `--rests`, à l'identique de `gram view` <Since v="1.4.0" />.

**Déroulement :**
<Steps>
1. **Mise en place** : vue globale et consolidée de l'ensemble des ingrédients nécessaires pour la recette (barre d'espace pour démarrer).

2. **Introduction de section** : récapitulatif des ingrédients requis pour la section imminente (affiché avant le début de chaque section).

3. **Étapes de préparation** : affichage progressif étape par étape dans une disposition en deux colonnes : ingrédients nécessaires à gauche, instructions à droite.

4. **Écran de synthèse** : récapitulatif du temps total écoulé.
</Steps>

Les ingrédients sont **agrégés par section** : les occurrences répétées d'un même ingrédient au sein d'une même section sont regroupées en une seule entrée avec mention de l'historique des quantités (ex. `200g beurre` suivi de `50g beurre` s'affiche `200g + 50g beurre`, sans addition arithmétique arbitraire). Le panneau latéral présente ainsi en un coup d'œil toutes les pesées requises pour la section.

**Minuteurs** — les minuteurs déclarés dans la recette (`~nom{30min}`) apparaissent dans l'écran de l'étape :
- Appuyez sur `T` pour lancer un minuteur ; en présence de plusieurs minuteurs concurrents, un menu de sélection est proposé.
- Les minuteurs s'exécutent en tâche de fond et demeurent visibles à mesure que vous progressez dans les étapes.
- Une alerte sonore de terminal retentit et l'affichage bascule sur l'état « terminé » dès que le décompte atteint zéro.
- `Q` ou `Échap` déclenchent une invite de confirmation de sortie afin d'éviter toute interruption accidentelle d'un minuteur actif.

**Raccourcis clavier :**
| Touche | Action |
|---|---|
| `Espace` / `Entrée` | Étape suivante |
| `B` | Étape précédente |
| `T` | Lancer un minuteur |
| `Q` / `Échap` | Quitter (demande confirmation si un minuteur est en cours d'exécution) |

- Options : `--scale <facteur|réf>`, `--skip-db`, `--db`.

#### `gram diff <fichier> [fichier-b]`
Affiche un diff sémantique de la recette (en comparant la structure logique des ingrédients, des minutages, des sections et des températures plutôt qu'une simple différence textuelle brute).
```bash
gram diff brioche.gram                        # Espace de travail vs HEAD (usage courant)
gram diff brioche.gram --ref HEAD~2           # Comparaison par rapport à un commit précis
gram diff brioche.gram --ref v1.2             # Comparaison par rapport à une étiquette git
gram diff brioche-v1.gram brioche-v2.gram     # Deux fichiers explicites (sans dépendance git)
```
La comparaison s'opère selon **sept axes distincts** :
- **Ingrédients** — quantités ajoutées, retirées ou modifiées, avec indication du pourcentage de variation (`percentChange`) lorsque les unités sont compatibles.
- **Minutages** — `totalTime`, `idleTime`, `activeTime`, `preparationTime` exprimés en minutes. La durée totale et le temps d'attente passif correspondent à l'ordonnancement par défaut (mise en place immédiatement avant chaque section), identiques aux valeurs de `gram view`.
- **Sections** — sections ajoutées ou supprimées et évolution du nombre d'étapes.
- **En-tête (frontmatter)** — modifications apportées aux champs `portions`, `description` et autres métadonnées. L'évolution de `title` est suivie séparément sur sa propre ligne au-dessus du bloc d'en-tête.
- **Préparations** — modifications des techniques de découpe et de préparation par ingrédient (ex. "en dés" → "émincé").
- **Températures & minuteurs** — cibles thermiques et durées de minuteurs ajoutées, supprimées ou modifiées par section.
- **Modules** — importations `@use` ajoutées, retirées, réassignées à un nouvel alias ou soumises à un facteur d'échelle distinct.

- Le diff s'appuie sur les objets compilés par le moteur Kitchen. Dès lors, un simple reformatage de style (espaces, retours à la ligne) ne produit aucune divergence sémantique.
- Le mode Git requiert que le fichier soit suivi par le gestionnaire de versions. Une erreur explicite est retournée si l'exécutable `git` n'est pas disponible dans l'environnement.
- Une section issue d'un import `@use` n'est jamais comptabilisée dans les axes Sections/Préparations/Températures/Minuteurs de la recette hôte — sans quoi l'adjonction d'une seule base donnerait l'illusion que l'ensemble des sections a été altéré. C'est l'axe Modules qui rend compte de l'import. `gram diff` ne résout pas les dépendances `@use` de manière récursive : chaque fichier étant compilé isolément, une modification opérée *à l'intérieur* d'une base importée n'apparaît pas ici — il convient de comparer directement le fichier de la base.
- Options : `--ref <réf-git>`.

#### `gram scale <fichier>`
Affiche un tableau comparatif avant/après des proportions d'ingrédients selon le facteur d'échelle choisi.
```bash
gram scale brioche.gram --scale 2            # Doubler l'ensemble des quantités
gram scale brioche.gram --scale 0.5          # Diviser par deux l'ensemble des quantités
gram scale brioche.gram --scale farine=300g  # Ajuster la recette sur une base de 300g de farine
gram scale brioche.gram --scale oeufs=3      # Ajuster la recette sur une base de 3 œufs
```
- Affiche un tableau comparatif : quantités d'origine (estompées) et quantités recalculées (mises en valeur).
- Les ingrédients non redimensionnables (valeurs qualitatives comme "1 pincée") sont répertoriés à part.
- Émet un avertissement pour les facteurs disproportionnés (inférieurs à ×0.1 ou supérieurs à ×20) et rappelle que les durées de cuisson ne sont jamais altérées arithmétiquement.
- Le mode par référence (`id=valeur`) calcule le multiplicateur à partir de la quantité nominale de l'ingrédient ciblé (l'identifiant doit correspondre à la clé canonique de l'ingrédient). Les conversions entre unités de même nature s'effectuent à la volée (ex. `farine=1kg` pour une recette formulée en `500g`). Le passage masse ↔ volume (ex. `eau=150g` pour une recette formulée en `ml`) est également assuré dès lors qu'une masse volumique est disponible (via `gram db enrich` ou une surcharge explicite `densities: ["eau:1.0"]` dans le frontmatter).
- Tous les ingrédients ne peuvent pas servir de référence : les ingrédients à quantité fixe (`@=`), les proportions relatives (`70% @&farine`), les ingrédients internes à une sous-recette (le produit fini parent constitue alors la référence valide), les alternatives conditionnelles et les ingrédients fragmentés entre unités incompatibles sont rejetés avec un message explicatif. Consultez la page [Comprendre l'ajustement des proportions](/fr/docs/explanation/scaling) pour l'inventaire complet des règles.
- Options : `--scale <facteur|réf>`, `--skip-db`, `--db`.

#### `gram watch [dossier]`
Surveille un répertoire et relance automatiquement `gram check` à chaque modification enregistrée de vos fichiers `.gram`.
```bash
gram watch                              # Surveille la racine du projet
gram watch recettes/                    # Surveille un dossier spécifique
gram watch --build --output ./dist      # Compile également les fichiers modifiés en JSON
```
- Affiche une ligne de résultat horodatée à chaque événement : `[12:34:01] ✓ brioche.gram` ou `✗ brioche.gram — 1 error`.
- Les erreurs sont détaillées directement sous le nom du fichier concerné. Le processus de surveillance ne s'interrompt jamais sur une erreur de validation.
- Un délai antirebond (*debounce*) de 150 ms prévient les exécutions redondantes lors des sauvegardes fragmentées par certains éditeurs.
- La modification d'une recette de base déclenche automatiquement la revalidation de tous les fichiers du dossier qui l'importent via `@use` (directement ou transitivement). Une mention `→ rechecking N dependent file(s)` indique le volume de recettes impactées.
- Options : `--build`, `--output/-o <dossier>`, `--skip-db`, `--db`.

#### `gram suggest`
Recherche dans votre collection les recettes réalisables à partir d'un ensemble donné d'ingrédients.
```bash
gram suggest --with "beurre, oeufs"
gram suggest --with "poulet" --without "crème"
gram suggest --with "citron, ail" --top 5 --min-match 50
gram suggest --with "butter" --json           # Résolution d'alias : butter → beurre
```
- Analyse l'ensemble des fichiers `.gram` en parallèle via l'analyseur syntaxique (sans exécuter le pipeline de compilation complet), garantissant une exécution quasi instantanée même sur des catalogues volumineux.
- **Correspondance tenant compte des alias** : lorsqu'une base de données est configurée, les désignations d'ingrédients sont résolues par l'index des alias. Une recherche sur `"butter"` associera ainsi les recettes contenant `@beurre`.
- Attribue un score de pertinence à chaque recette sous la forme d'un pourcentage (`correspondance / total ingrédients recherchés`). Spécifiez `--min-match` pour filtrer les correspondances partielles.
- L'option `--without` élimine immédiatement toute recette faisant appel à l'un des ingrédients exclus.
- Options : `--with/-w <csv>`, `--without <csv>`, `--top/-n <n>` (par défaut 10), `--min-match <0–100>` (par défaut 1), `--pattern <glob>`, `--db`, `--skip-db`, `--json`.

#### `gram print <fichier>`
Génère un document HTML prêt pour l'impression et l'ouvre dans le navigateur par défaut.
```bash
gram print brioche.gram                   # Génération et ouverture
gram print brioche.gram --scale 2         # Impression avec proportions doublées
gram print brioche.gram --no-open         # Génération seule et affichage du chemin sur stdout
```
- Le document HTML est généré dans un fichier temporaire (`gram_print_<horodatage>.html` au sein du répertoire temporaire du système d'exploitation) et ouvert via la commande native appropriée (`open` sous macOS, `xdg-open` sous Linux, `cmd /c start` sous Windows).
- Le rendu est strictement identique à `gram export --format html` — idéal pour déclencher la boîte de dialogue d'impression du navigateur (`Ctrl+P` / `Cmd+P`) et obtenir un PDF au format A4.
- `--no-step-qty` — masque le rappel des quantités au sein du texte descriptif des étapes (particulièrement utile lorsque l'on cuisine en se référant à la liste d'ingrédients en marge).
- Options : `--no-open`, `--scale <facteur|réf>`, `--no-step-qty`, `--skip-db`, `--db`, `--bakers-math`, `--bakers-reference <id>`, `--bakers-math-only`, `--nutrition <base>`, `--mise-en-place <mode>`, `--rests <choice>`.
- `--nutrition <auto|total|per-portion|per-100g>` <Since v="1.1.0" /> sélectionne la base nutritionnelle du document (par défaut `auto` : par portion si `portions:` est déclaré, sinon pour toute la recette). `per-100g` calcule les valeurs pour 100 g de préparation brute assemblée — voir [Estimation nutritionnelle](/fr/docs/explanation/nutrition).
- `--mise-en-place <per-section|upfront|per-session>` <Since v="1.4.0" /> définit l'ordonnancement de la mise en place (par défaut `per-section`), ajustant en conséquence la durée totale et le temps d'attente passif dans l'en-tête imprimé. Voir [Quand se fait la mise en place](/fr/docs/reference/syntax/times#quand-se-fait-la-mise-en-place).
- `--rests <shortest|balanced|longest>` <Since v="1.4.0" /> définit la résolution des durées variables pour les minuteurs passifs (`~_{12-24h}`) : durée minimale (`shortest`, par défaut), médiane (`balanced`) ou maximale (`longest`). Les durées exactes et les minuteurs actifs ne sont pas affectés.
- `--serve`, `--tz`, `--available` <Since v="1.4.0" /> projettent l'ordonnancement sur le calendrier réel selon le moteur de rétro-planning de `gram plan` : chaque étape reçoit une heure locale précise (avec indication des changements de journée et des plages de temps passif), et l'en-tête consigne l'heure de service ciblée ainsi que les contraintes non résolues. Nécessitent impérativement `--serve`.
- `--with-sheet` <Since v="1.4.0" /> (avec `--serve`) : adjoint la fiche de production détaillée à la suite de la recette dans le même document.

#### `gram export <fichier>`
Exporte une recette vers Markdown ou vers un document HTML prêt pour l'impression.
```bash
gram export brioche.gram --format md                   # Génère brioche.md à côté de la source
gram export brioche.gram --format html -o ~/print.html # Destination explicite
gram export brioche.gram --format html --scale 2       # Export avec proportions doublées
```
- `--format md` — Markdown standard structuré avec liste de courses, inventaire du matériel et étapes numérotées.
- `--format html` — Document HTML autonome formaté pour l'impression A4 avec styles CSS intégrés et icônes vectorielles SVG Lucide (sans dépendances externes d'icônes). Les polices typographiques Courier Prime et Inter sont appelées depuis Google Fonts via une directive `@import` CSS, nécessitant un accès réseau lors de l'ouverture initiale.
- Chemin de destination par défaut : même répertoire que le fichier source, l'extension `.gram` étant remplacée par `.md` ou `.html`.
- `--no-step-qty` — masque les quantités au sein des étapes descriptives. **Format HTML uniquement** — sans effet avec `--format md`. La liste d'ingrédients introductive de chaque section conserve toujours ses dosages intégraux.
- Options : `--format md|html`, `--output <chemin>`, `--scale <facteur|réf>`, `--no-step-qty`, `--skip-db`, `--db`, `--bakers-math`, `--bakers-reference <id>`, `--bakers-math-only`, `--nutrition <base>`, `--mise-en-place <mode>`, `--rests <choice>`.
- `--nutrition <auto|total|per-portion|per-100g>` <Since v="1.1.0" /> sélectionne la base nutritionnelle (par défaut `auto` : par portion si `portions:` est déclaré, sinon pour la recette entière).
- `--mise-en-place <per-section|upfront|per-session>` <Since v="1.4.0" /> ajuste l'ordonnancement de la mise en place (par défaut `per-section`), recalculant la durée totale et le temps d'attente passif dans l'en-tête exporté. En HTML, le mode `per-section` insère également un libellé « Mise en place » au-dessus des ingrédients de chaque section. Voir [Quand se fait la mise en place](/fr/docs/reference/syntax/times#quand-se-fait-la-mise-en-place).
- `--rests <shortest|balanced|longest>` <Since v="1.4.0" /> définit la résolution des durées variables pour les minuteurs passifs (`~_{12-24h}`).
- `--serve`, `--tz`, `--available` <Since v="1.4.0" /> projettent la recette sur le calendrier réel selon le moteur de rétro-planning de `gram plan`. Nécessitent impérativement `--serve`.
- `--with-sheet` <Since v="1.4.0" /> (avec `--serve`) : insère la fiche de production détaillée à la suite de la recette dans le document exporté.

#### `gram plan <fichier>` <Since v="1.4.0" />
Planifie une recette à rebours depuis l'heure de service ciblée et génère une fiche de production détaillée indiquant quand débuter chaque tâche en tenant compte de vos plages réelles de disponibilité.
```bash
gram plan pain.gram --serve "2026-10-11 13:00" --tz Europe/Paris --available 08:00-22:00
gram plan pain.gram --serve "2026-10-11 13:00" --available 08:00-22:00 --available sat=09:00-23:00 --available 2026-10-09=none
gram plan pain.gram --serve "2026-10-11 13:00" --format md        # Sortie Markdown au lieu de texte brut
gram plan pain.gram --serve "2026-10-11 13:00" --ics pain.ics     # Génère également un calendrier iCalendar
```
- `--serve "<date> <heure>"` (obligatoire) : heure cible du service, formulée sous forme de date et heure locales dans le fuseau horaire spécifié.
- `--tz <fuseau>` : identifiant de fuseau horaire IANA (ex. `Europe/Paris`). Par défaut : valeur du paramètre `timezone` du projet (ou de votre configuration globale), à défaut le fuseau local du système. C'est à partir de cette référence que sont interprétés l'heure du service, les plages de disponibilité et les décalages d'heure d'été/d'hiver.
- `--available <plage>`, répétable : définit vos fenêtres de disponibilité pour le travail actif en cuisine. `08:00-22:00` s'applique à tous les jours ; un préfixe de jour (`fri=18:00-22:00`, de `mon` à `sun`) restreint la règle au jour indiqué ; un préfixe de date (`2026-10-09=none`) surcharge une date précise (`none` indiquant une indisponibilité absolue). Plusieurs plages peuvent être associées à une même clé en les séparant par des virgules (`sat=08:00-09:00,18:00-22:00`), et une plage dont l'heure de fin est inférieure à l'heure de début traverse minuit. En l'absence de flag, vous êtes considéré disponible 24h/24.
- Les minuteurs passifs définis par une plage (`~_{8-16h}`) sont automatiquement ajustés (étirés ou réduits) par le planificateur pour maintenir les tâches actives au sein de vos créneaux disponibles ; la fiche de production détaille les ajustements opérés et consigne les éventuelles contraintes insolubles. Voir [Planifier en heures réelles](/fr/docs/explanation/planning-in-real-time/).
- `--format text|md|html|json` : format de restitution (par défaut `text`). L'option `json` fournit l'objet structuré `{ plan, runSheet }`.
- `--ics <fichier>` : génère un fichier de calendrier iCalendar standardisé (`.ics`) contenant un événement par tâche planifiée (horodaté en UTC, votre agenda l'affichant dans son propre fuseau local) et une notification de rappel 5 minutes avant chaque étape exigeant une action manuelle. Le message de confirmation étant émis sur `stderr`, la commande demeure parfaitement composable via un tube de redirection (`|`).
- `--mise-en-place`, `--rests`, `--scale` et `--stock` fonctionnent de manière identique à `gram view`. `--now <instant>` définit l'instant de référence (par défaut, l'heure courante) servant à lever un avertissement si la première tâche aurait déjà dû être entamée dans le passé.

#### `gram format [motif]`
Formate automatiquement les fichiers `.gram` en place en appliquant 13 règles canoniques issues de `@gram-lang/format`.
```bash
gram format                              # Formater l'ensemble des fichiers *.gram
gram format brioche.gram                 # Formater un fichier unique
gram format "recettes/**/*.gram" --check # Vérification CI — code de sortie 1 si un fichier doit être formaté
```
**13 règles canoniques appliquées :**
1. **Normalisation du frontmatter** — standardisation des délimiteurs et élimination des espaces superflus
2. **Titres de section** — espace unique après les marqueurs `##`
3. **Numérotation des étapes** — préfixes d'étape standardisés (`1. `)
4. **Verbes d'action** — préfixes d'action normalisés (`[Mélanger]`)
5. **Syntaxe des ingrédients** — espacement et normalisation des accolades `@ingrédient{qte}`
6. **Syntaxe du matériel** — espacement et normalisation `#matériel{qte}`
7. **Syntaxe des minuteurs** — espacement des minuteurs actifs `~minuteur{durée}` et passifs `~_minuteur{durée}`
8. **Syntaxe des températures** — formatage standardisé `^temp{valeur}`
9. **Déclarations et références d'intermédiaires** — espacement canonique `->&pâte` et `&pâte`
10. **Syntaxe composite** — formalisme des ingrédients composites `<@parent`
11. **Zéros décimaux superflus** — simplification numérique `{500.0g}` → `{500g}`, `{1.50g}` → `{1.5g}`
12. **Mise en forme des commentaires** — espacement standardisé après les doubles barres (`//`)
13. **Nettoyage des espaces et saut de ligne final (EOF) unique**

Compte-rendu par fichier : `✔ brioche.gram  2 IDs lowercased · 1 trailing zero removed`
Le formateur est strictement idempotent : l'exécuter plusieurs fois de suite ne modifiera jamais le code après la première passe.
- Options : `--check`.

### Gestion de la base de données

Commandes associées à `gram db` pour administrer votre référentiel d'ingrédients `ingredients.yaml`.

:::tip[Enchaînement Recommandé]
Respectez scrupuleusement cet ordre d'exécution :
```
gram db sync → gram db lint → gram db enrich
```
Exécuter `lint` avant `enrich` évite de consommer inutilement des jetons d'IA sur des doublons voués à être fusionnés.
Utilisez `gram db search` à tout moment pour auditer l'exhaustivité de vos fiches, et `gram db merge` pour intégrer un référentiel tiers au vôtre.
:::

<Steps>
1. #### `gram db sync [motif]`
   Parcourt vos recettes pour identifier les ingrédients non répertoriés et les insérer dans la base de données.
   - L'assistant interactif d'appariement flou (distance de Levenshtein) vous permet de prévenir les doublons (fautes de frappe, formes plurielles).
   - Options : `--dry-run/-n` (simulation sans écriture), `--db <chemin>`.

2. #### `gram db lint`
   Fait appel à l'IA pour détecter et résoudre les doublons sémantiques et les pluriels dans votre base de données.
   - Identifie les doublons multilingues (ex. `sucre` / `sugar`) et les formes plurielles (ex. `oeufs` → `oeuf`).
   - Pour chaque ambiguïté, vous déterminez la clé canonique à conserver. La désignation écartée est automatiquement consignée comme alias.
   - Présente un diff nutritionnel ciblé (uniquement les valeurs divergentes) lorsque les deux fiches comportent des données contradictoires, permettant un arbitrage éclairé.
   - Signale les ingrédients dont les dénominations ou les alias deviendraient indifférenciables une fois normalisés (ex. `Huile d'olive` et `huile-dolive`), garantissant qu'aucune recette ne cible silencieusement une entrée erronée.
   - Options : `--report/-r` (inventaire des anomalies sans application des modifications), `--db <chemin>`, ainsi que les [options IA communes](#choisir-le-modèle-ia).

3. #### `gram db enrich`
   <Since v="1.1.0" type="changed" />
   Interroge l'IA pour suggérer les données manquantes dans votre référentiel, puis vous soumet chaque proposition à validation interactive avant toute écriture sur le disque.
   - Propose des valeurs par lots pour les champs `density`, `unit_weight`, `nutrition`, `category` et `tags` (`unit_weight` étant complété conjointement avec `density`). `category` représente la famille culinaire (ex. Légumes, Produits laitiers, Céréales) — à distinguer des `tags` taxonomiques libres.
   - `category` et `tags` sont appliqués automatiquement ; les valeurs de `density`, `unit_weight` et `nutrition` font l'objet d'une validation unitaire interactive (accepter, corriger ou ignorer), car elles sont tributaires des spécificités précises de vos approvisionnements réels.
   - Toute valeur validée sans modification est annotée du marqueur `# [LLM]` dans `ingredients.yaml`, permettant de distinguer les estimations générées par l'IA non révisées manuellement.
   - Peut être réexécuté sans risque : seules les propriétés encore vacantes sont soumises à enrichissement.
   - Options : `--ingredient <slug>` (enrichir une entrée isolée), `--field density|nutrition|tags|category|all` (par défaut `all`), `--yes/-y` (ignorer la revue manuelle et tout accepter automatiquement — pour les scripts automatisés), `--report/-r` (simulation des propositions sans écriture), `--db <chemin>`, ainsi que les [options IA communes](#choisir-le-modèle-ia).
</Steps>

#### `gram db validate`
<Since v="1.1.0" />

Vérifie l'intégrité globale de votre fichier `ingredients.yaml`.
- Détecte les infractions de schéma, les alias redondants et les valeurs aberrantes (ex. densité > 2.5).
- Une fiche erronée n'interrompt pas la validation de l'ensemble du fichier : chaque entrée est évaluée indépendamment et le rapport synthétise la totalité des anomalies identifiées en une seule passe.
- Options : `--strict` (renvoie un code d'erreur 1 en présence de simples avertissements, adapté à l'intégration continue).

#### `gram db search [requête]`
Recherche et affiche le détail complet des fiches d'ingrédients.
```bash
gram db search beurre            # Recherche partielle sur id, nom ou alias
gram db search --tag laitier     # Ingrédients associés au tag 'laitier'
gram db search --category Grains # Ingrédients de la catégorie Grains
gram db search --missing nutrition  # Fiches dépourvues de données nutritionnelles
gram db search --exact beurre --count  # Affiche uniquement le décompte des correspondances
```
- Options : `--tag <tag>`, `--category/-c <category>`, `--missing nutrition|physical|aliases`, `--exact`, `--count`, `--json`, `--db <chemin>`.

#### `gram db merge <source.yaml>`
Fusionne un référentiel d'ingrédients externe avec votre base locale.
```bash
gram db merge ~/shared-ingredients.yaml          # Résolution interactive des conflits
gram db merge community.yaml --prefer remote     # Privilégie systématiquement les valeurs externes en cas de conflit
gram db merge community.yaml --only-new          # Insère uniquement les nouvelles entrées, sans arbitrage de conflit
```
La fusion s'appuie sur la **résolution des alias** : si votre base contient `butter` avec pour alias `beurre`, et que le fichier source propose une entrée `beurre`, elles sont reconnues comme désignant un ingrédient identique.
- Options : `--prefer local|remote` (par défaut `local`), `--dry-run`, `--only-new`, `--db <chemin>`.

## Détails du fichier de configuration

Le CLI consolide la configuration en fusionnant les paramètres issus de `~/.config/gram/config.yaml` (niveau global) et de `.gram/config.yaml` (niveau projet).

### Choisir le modèle IA

<Since v="1.1.0" />

Toutes les commandes sollicitant des capacités d'IA — `gram import`, `gram db lint` et `gram db enrich` — acceptent les mêmes options et mentionnent explicitement le modèle ciblé avant l'exécution, prévenant toute dépense imprévue de jetons :

```bash
gram import recette.json --model gemini-3.1-pro   # Valable pour cette exécution uniquement
gram db enrich --provider anthropic               # Valable pour cette exécution uniquement
gram db lint --pick-model                         # Sélection interactive
```

- `--model <nom>` — exploite un modèle spécifique pour cette exécution sans altérer le fournisseur.
- `--provider <google|openai|anthropic|ollama>` — sélectionne un fournisseur spécifique pour cette exécution. Le fournisseur n'est jamais inféré à partir du nom du modèle.
- `--pick-model` — sélectionne interactivement le fournisseur et le modèle dans un menu. Requiert un terminal interactif (dans les scripts automatisés, privilégiez `--provider`/`--model`).

Aucun de ces drapeaux n'altère votre fichier de configuration persistant. Pour redéfinir la valeur par défaut de manière pérenne, utilisez `gram config set ai.model <nom>` ou réexécutez `gram init`.

Lorsque `--provider` (ou `--pick-model`) spécifie un fournisseur non déclaré dans votre configuration, les paramètres `model`, `apiKey` et `baseUrl` définis sous le bloc `ai:` ne sont **pas** reportés : ils demeurent associés au fournisseur pour lequel ils ont été rédigés. Gram réclamera la variable d'environnement dédiée au nouveau fournisseur. Cette règle s'applique aussi bien si le bloc `ai:` cible un autre prestataire que s'il n'en précise aucun : une section dépourvue de `provider:` est rattachée au fournisseur déterminé par autodétection par Gram, et non au prestataire spécifié manuellement en ligne de commande.

### Configuration IA en cascade
Gram utilise une hiérarchie de résolution en cascade pour la gestion des clés secrètes d'API :
1. **Variables d'environnement** : la variable assignée au fournisseur sollicité — `GEMINI_API_KEY`, `OPENAI_API_KEY` ou `ANTHROPIC_API_KEY` (issue de l'environnement système ou d'un fichier `.env`) — a toujours priorité absolue. Il s'agit de la méthode **recommandée** pour sécuriser vos identifiants en environnement local comme en intégration continue.
2. **Repli sur `config.yaml`** : si la variable d'environnement fait défaut, Gram consulte le champ `ai.apiKey` de votre fichier `config.yaml` — mais uniquement si ce paramètre a été défini pour le fournisseur effectivement sollicité.

Une clé secrète n'est jamais transmise d'un fournisseur à un autre. Si vous avez configuré `provider: openai` alors que seule la variable `GEMINI_API_KEY` est renseignée, Gram suspend son exécution et réclame `OPENAI_API_KEY` plutôt que de router votre clé Google vers l'API d'OpenAI. Le même principe d'isolation prévaut entre les niveaux de configuration : un bloc `ai:` global est ignoré si le projet local déclare un fournisseur distinct.

:::caution[Protégez vos Clés !]
Ne renseignez jamais votre clé `apiKey` en clair dans `config.yaml` si votre répertoire `.gram` est suivi sous Git : votre identifiant d'API serait exposé publiquement.
:::

### Paramètres de `config.yaml`

Voici la référence exhaustive des paramètres disponibles dans `config.yaml` :

```yaml
version: 1                     # Réservé aux futures migrations de structure — non exploité actuellement
database: ".gram/ingredients.yaml" # Chemin relatif ou absolu vers le fichier de base de données
language: "fr"                 # Langue cible pour l'ensemble des contenus générés par l'IA
                               # Pris en charge : en, fr, de, es, it, pt, nl, ja, zh — défaut : en
timezone: "Europe/Paris"       # Fuseau horaire IANA de référence pour votre cuisine (valeur par défaut de `gram plan --tz`)
                               # En son absence, le fuseau système est utilisé. Modification : `gram config set timezone <fuseau>`
updateCheck: true             # Désactivez (false) pour masquer la notification de mise à jour à l'issue des commandes

# Alias d'importation pour les modules `@use` — `@use "@bases/pate.gram"` résout vers
# "<racine du projet>/partage/bases/pate.gram". Voir la référence des imports de modules.
paths:                         # Introduit en v1.2.0 pour les alias de modules
  bases: "./partage/bases"

# Paramètres d'IA pour `gram import`, `gram db enrich` et `gram db lint`
ai:
  # Fournisseurs pris en charge : "google", "openai", "anthropic", "ollama"
  provider: "google"

  # Identifiant du modèle cible (par défaut 'gemini-3.5-flash' pour google,
  # 'gpt-4.1-nano' pour openai, 'claude-haiku-4-5-20251001' pour anthropic, 'llama4' pour ollama)
  model: "gemini-3.5-flash"

  # Clé d'API. Privilégiez systématiquement la variable d'environnement appropriée :
  # GEMINI_API_KEY (google), OPENAI_API_KEY (openai), ANTHROPIC_API_KEY (anthropic).
  # Ce champ n'est lu que pour le fournisseur mentionné ci-dessus — il est ignoré sous
  # l'option --provider ou lorsqu'un autre prestataire est requis. Ollama ne requiert aucune clé.
  # ATTENTION : Utilisez un fichier .env plutôt que de versionner votre clé dans ce fichier.
  apiKey: "VOTRE_CLE_API"

  # URL racine d'API personnalisée — exclusivement lue pour le fournisseur "ollama".
  # Vaut "http://localhost:11434/v1" (ou la variable OLLAMA_BASE_URL) par défaut.
  baseUrl: "http://localhost:11434/v1"
```
