Enrichit un `CompilationResult` (issu de `@gram-lang/kitchen`) avec des propriétés physiques (masse standardisée, rendement d'achat, estimations nutritionnelles et pourcentages du boulanger) en les croisant avec une base de données d'ingrédients. Il s'agit de la seule étape du pipeline qui requiert une base de données : l'analyse syntaxique et la compilation fonctionnent de manière pure sur n'importe quel texte `.gram`, sans la moindre dépendance externe.

## `analyze`

```typescript
function analyze(
  result: CompilationResult,
  database: Record<string, IngredientData>,
  options?: AnalyzerOptions,
): AnalysisResult

interface AnalysisResult {
  result: AnalyzedCompilationResult;
  missingIngredients: string[]; // identifiants présents dans la recette mais absents de `database`
}
```

```typescript
import { compile } from '@gram-lang/kitchen';
import { analyze } from '@gram-lang/analyzer';

const compiled = compile(ast);
const { result: analyzed, missingIngredients } = analyze(compiled, myIngredientDatabase);
```

> La base de données d'ingrédients est le **deuxième argument positionnel**, et non une propriété de l'objet `options` : `analyze(compiled, database, options?)`.

`analyze()` est une fonction pure qui ne modifie jamais son argument `result`. L'objet `AnalyzedCompilationResult` étend `CompilationResult` en y intégrant les propriétés physiques pour chaque utilisation d'ingrédient (`normalizedMass`, `conversionMethod`, `isEstimate`, `purchasingMass`, `bakersPercentage`), ainsi qu'un bloc de métriques `metrics.nutrition`. Consultez la page [Formats de données](/fr/docs/reference/api/data-formats) pour un exemple entièrement annoté.

### `AnalyzerOptions`

Toutes les options d'enrichissement sont activées par défaut (via des vérifications internes `!== false`). Il suffit de transmettre la valeur explicite `false` pour désactiver une passe de calcul spécifique.

| Option | Type | Description |
|---|---|---|
| `enableMassStandardization` | `boolean` | Convertit les quantités d'ingrédients en masses standardisées en grammes. |
| `enableYieldCalculation` | `boolean` | Applique le facteur de rendement d'épluchage/parage `physical.yield` de la base de données. |
| `enableNutritionalEstimation` | `boolean` | Calcule les macronutriments et calories de `metrics.nutrition` (au global et par portion). |
| `enableBakersMath` | `boolean` | Calcule `bakersPercentage` par rapport à l'ingrédient marqué `*` (ou `bakersReference`). |
| `bakersReference` | `string` | Identifiant explicite de l'ingrédient servant de base 100 % au pourcentage du boulanger. |
| `portions` | `number` | Remplace le nombre de portions du frontmatter pour le diviseur de `metrics.nutrition.perPortion`. |
| `lang` | `string` | Code de langue (ex. : `'en'`, `'fr'`) pour la normalisation des unités et le tri des catégories. |

## `validateIngredientDatabase`

```typescript
function validateIngredientDatabase(rawDb: unknown): {
  data: Record<string, IngredientData>;
  rejected: { key: string; message: string }[];
}
```

Valide la base entrée par entrée plutôt que selon une approche tout-ou-rien : une entrée malformée n'interrompt pas le chargement des autres ingrédients valides. Transmettez `data` au pipeline et remontez les anomalies du tableau `rejected` à l'utilisateur (par exemple via la commande `gram db validate`). Consultez [Formats de données](/fr/docs/reference/api/data-formats) pour le schéma YAML détaillé de `IngredientData`.

## Utilitaires de masse

```typescript
function standardizeMass(
  amount: number,
  unit: string,
  database: Record<string, IngredientData>,
  ingredientName?: string,
  overrides?: Record<string, number>, // slug -> densité (g/mL) ou poids unitaire (g), issu du frontmatter `densities:`
  lang?: string,
): { mass: number; method: "physical" | "density" | "unit_weight" | "default" | "explicit"; isEstimate: boolean } | null

function convertUnit(value: number, fromUnit: string, toUnit: string, density?: number, lang?: string): number | null

function applyYield(
  mass: number,
  method: "physical" | "density" | "unit_weight" | "default" | "explicit",
  yieldFactor?: number,
): { normalizedMass: number; purchasingMass?: number }
```

`standardizeMass` résout une quantité en grammes selon la cascade de priorité suivante : (1) conversion directe si l'unité est une masse (`g`, `kg`, `oz`...), (2) conversion volumétrique via la densité volumique résolue de l'ingrédient, (3) conversion de comptage si l'unité est une pièce (`gousse`, `tranche`...) via le poids unitaire `unit_weight`. La fonction retourne `null` (sans jamais extrapoler à l'aveugle) lorsqu'une unité de volume ne dispose d'aucune densité connue.

`convertUnit` convertit une valeur entre deux unités arbitraires et permet le passage masse↔volume dès qu'une `density` (exprimée en g/mL) est fournie. Elle renvoie `null` lorsque la conversion inter-famille est impossible faute de densité.

## `calculateNutrition`

```typescript
function calculateNutrition(
  ingredients: AnalyzedUsage[],
  database: Record<string, IngredientData>,
  portions?: number,
  massStatus?: 'precise' | 'estimated' | 'incomplete',
): NutritionMetrics
```

Aplatit les ingrédients composites et les alternatives (en retenant la première option), ignore les ingrédients facultatifs (`optional`) et les quantités nulles, puis cumule les valeurs nutritionnelles (déclarées **pour 100 g** dans la base de données — voir [Formats de données](/fr/docs/reference/api/data-formats)) proportionnées à la masse standardisée de chaque ingrédient. Retourne `isEstimate: true` si au moins une masse contributrice reposait sur une estimation, ainsi qu'un taux de couverture `coverage` de 0 à 1 (fraction d'ingrédients documentés).

La structure `NutritionMetrics` expose le profil nutritionnel sous trois référentiels complémentaires :

```typescript
interface NutritionMetrics {
  total: Macros;          // l'ensemble de la recette, selon ses proportions compilées ou mises à l'échelle
  perPortion?: Macros;    // calculé dès que le nombre de portions est renseigné
  per100g?: Macros;       // pour 100 g de préparation ayant contribué aux macros
  portions?: number;      // le diviseur appliqué pour calculer perPortion
  basis?: { mass: number; massStatus?: 'precise' | 'estimated' | 'incomplete' };
  isEstimate: boolean;
  coverage: number;
  warnings?: Warning[];
}
```

Chaque référentiel est calculé directement à partir des sommes non arrondies et fait l'objet d'un arrondi indépendant, évitant ainsi toute accumulation d'erreurs d'arrondi entre le total et la portion individuelle. La propriété `basis` représente le dénominateur de masse utilisé pour le calcul `per100g` — consultez le guide [Estimation nutritionnelle](/fr/docs/explanation/nutrition/) pour comprendre sa méthode de calcul en l'absence de perte hydrique à la cuisson.

L'inventaire des nutriments gérés, leurs unités et leurs règles d'arrondi proviennent d'une table unique exportée `NUTRIENTS`, assurant une parité stricte entre `gram db enrich`, `gram db lint`, `gram db search`, l'infobulle du serveur LSP et l'ensemble des moteurs de rendu.

## `diffRecipes`

```typescript
function diffRecipes(a: CompilationResult, b: CompilationResult): DiffResult
```

Calcule le diff structurel entre deux recettes compilées (par exemple deux révisions d'un même fichier, ou la version de base comparée à sa version ajustée). Il détecte les variations de quantités ou d'unités d'ingrédients (avec calcul de `percentChange`), les modifications de préparation, les deltas d'ordonnancement (`totalTime`, `idleTime`, `activeTime`, `preparationTime`), les ajouts, suppressions ou remaniements de sections, les variations de température et de durée, ainsi que les modifications du frontmatter (`meta`). La propriété `hasChanges` vaut `true` dès qu'un écart est identifié.

Les écarts de durée comparent les temps de l'ordonnancement théorique par défaut (`schedule`) : `totalTime`, `idleTime`, `activeTime` et `preparationTime` proviennent tous de `schedule`. Un minuteur actif défini par un intervalle (`~{20-25min}`) retient sa borne maximale par sécurité. Ces repères temporels sont rigoureusement identiques des deux côtés de la comparaison et correspondent à la vue par défaut générée par `gram view`. *(Depuis la 1.4.0. Les versions antérieures lisaient les champs dépréciés `metrics.totalTime` et `metrics.idleTime`, qui décrivaient la stratégie historique où toute la préparation était placée au démarrage).*

Une section importée via une directive modulaire `@use` (marquée par `ProcessedSection.module`) est isolée des comparaisons d'étapes : cela évite qu'un simple import additionnel ne décale l'index de toutes les sections subséquentes et ne produise un diff artificiel. Son import fait l'objet d'une comparaison autonome par triplet `(uri, binding, facteur d'échelle)` dans le tableau `modules: ModuleDelta[]` — tout import réassigné ou dont le multiplicateur varie est signalé avec le statut `"changed"`.
