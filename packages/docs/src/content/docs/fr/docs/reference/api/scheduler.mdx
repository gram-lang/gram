Le moteur d'ordonnancement de Gram prend en entrée un **graphe de tâches** agnostique (le champ `tasks` d'une recette compilée) et répond à deux questions fondamentales : comment ces tâches s'articulent-elles chronologiquement (`layout`), et à quel moment précis démarrer chaque tâche compte tenu de l'heure de service visée et des disponibilités de l'utilisateur (`project`).

Le scheduler ne possède aucune connaissance de l'AST ou de la syntaxe `.gram` : il opère exclusivement sur le graphe de tâches. Consultez [Le moteur d'ordonnancement](/fr/docs/explanation/engine/scheduler/) pour approfondir son architecture interne et [Planifier en heures réelles](/fr/docs/explanation/planning-in-real-time/) pour ses cas d'usage pratiques.

:::note[Fonctions pures et déterminisme]
Chaque fonction du moteur est pure : à entrées identiques correspondent toujours des sorties strictement identiques. Aucune donnée n'est lue sur l'environnement d'exécution (ni horloge système, ni fuseau horaire local), et les objets passés en paramètre ne sont jamais mutés.
:::

```bash
npm install @gram-lang/scheduler
```

Le compilateur `@gram-lang/kitchen` réexporte déjà `layout`, `LayoutOptions` et les constantes associées (`MISE_EN_PLACE_MODES`, `REST_CHOICES`...) : les applications n'utilisant que Kitchen n'ont pas besoin d'installer directement ce paquet.

## `layout`

```typescript
function layout(graph: TaskGraph, options?: LayoutOptions): LayoutResult

interface LayoutOptions {
  miseEnPlace?: MiseEnPlaceMode; // "perSection" (défaut) | "upfront" | "perSession"
  rests?: RestChoice;            // "shortest" (défaut) | "balanced" | "longest"
  restOverrides?: Record<string, number>; // durées passives cibles en minutes, par identifiant de tâche (utilisé par project())
}

interface LayoutResult {
  schedule: Schedule;
  diagnostics: SchedulingDiagnostic[];
}
```

Positionne le graphe de tâches sur une chronologie relative, exprimée en minutes à partir de l'instant 0 (démarrage de la première tâche).

Le travail actif est systématiquement planifié sur sa durée nominale (`nominal`), indépendamment de l'option `rests`. Pour les durées passives exprimées sous forme de fourchette, l'option `rests` sélectionne la borne minimale (`shortest`), la valeur médiane (`balanced`) ou la borne maximale (`longest`). Les temps passifs à durée fixe ainsi que les minuteurs actifs ne sont pas modifiés.

Toute valeur passée dans `restOverrides` qui excèderait la fourchette autorisée d'un temps passif est ignorée : aucune durée passive n'est étirée ou compressée au-delà des limites définies par la recette.

```typescript
import { compile } from '@gram-lang/kitchen';
import { layout } from '@gram-lang/scheduler';

const { tasks } = compile(ast);

const { schedule, diagnostics } = layout(tasks, {
  miseEnPlace: 'upfront',
  rests: 'longest',
});
// schedule.totalTime, schedule.blocks, schedule.sessions...
```

Par défaut, la propriété `compiled.schedule` d'une recette compilée correspond exactement à `layout(compiled.tasks).schedule`.

### `Schedule`

```typescript
interface Schedule {
  miseEnPlace: MiseEnPlaceMode;
  rests: RestChoice;
  totalTime: number;       // fin la plus tardive parmi l'ensemble des blocs
  activeTime: number;      // durée totale du travail actif, mise en place exclue
  preparationTime: number; // durée de la mise en place (somme des tâches `prep`)
  idleTime: number;        // temps d'inactivité global : totalTime - activeTime - preparationTime
  blocks: ScheduleBlock[]; // triés par heure de début, puis par heure de fin
  sessions: ScheduleSession[]; // une par journée de travail, de la plus lointaine au jour J
}

type ScheduleBlock =
  | { kind: "prep"; task: string; section: number; start: number; end: number; deferred?: true; items?: MiseEnPlaceItem[] }
  | { kind: "step"; task: string; section: number; step: number; start: number; end: number }
  | { kind: "passive"; task: string; section: number; step: number; track?: string; start: number; end: number };

interface ScheduleSession {
  day: number;      // 0 = jour de service (J), 1 = veille (J-1, ~{-1d})...
  start: number;    // bornes de début et fin du travail actif de la session
  end: number;
  sections: number[];
}
```

Lorsqu'un bloc `prep` regroupe plusieurs préparations partageant les mêmes bornes de début et de fin, son champ `task` reçoit l'identifiant de la première tâche du groupe.

### `SchedulingDiagnostic`

Diagnostics structurels émis par `layout()` sous forme de données neutres (Kitchen les convertit ensuite en avertissements utilisateur) :

```typescript
type SchedulingDiagnostic =
  | { code: "TIME_PARADOX"; section: number; pulledTo: number }
  | { code: "TRACK_CONTENTION"; section: number; trackName: string; delay: number }
  | { code: "SESSION_OVERFLOW"; section: number; day: number; overflowMinutes: number };
```

Le code `SESSION_OVERFLOW` signale que le travail actif d'une session déborde en amont de la fenêtre de 24 heures allouée à cette journée de travail (repoussé par l'enchaînement des étapes). Seul le travail actif est pris en compte dans cette limite, et non les temps passifs franchissant la nuit.

## Le graphe de tâches

```typescript
interface TaskGraph {
  tasks: Task[];                // ordonnancées par sections puis étapes, la tâche prep en tête de section
  sections: TaskGraphSection[]; // structure parallèle aux sections de la recette
}

type Task = PrepTask | StepTask | TimerTask;

interface TaskDuration {
  nominal: number; // durée de référence utilisée par défaut
  min?: number;    // uniquement pour un temps passif exprimé en fourchette
  max?: number;
}

interface PrepTask {
  id: string;
  kind: "prep";
  section: number;
  intermediate?: string; // défini pour la préparation d'un intermédiaire (&pâte)
  duration: TaskDuration;
  items: MiseEnPlaceItem[];
  after: string[];       // étape produisant l'intermédiaire (si déjà résolue)
}

interface StepTask {
  id: string;
  kind: "step";
  section: number;
  step: number;          // indice de l'étape au sein de la section (commentaires inclus)
  duration: TaskDuration;
  produces?: string[];   // intermédiaires déclarés dans la recette
  consumes?: string[];
  after: string[];
}

interface TimerTask {
  id: string;
  kind: "passive";
  section: number;
  step: number;
  track?: string;        // piste d'équipement dédiée (~_four{})
  offset: number;        // décalage en minutes par rapport au début de l'étape
  duration: TaskDuration;
  after: string[];
}

interface TaskGraphSection {
  day: number;           // 0 = jour de service ; une ancre en jours initie une nouvelle journée
  deadline?: number;     // ancre temporelle, en minutes avant l'échéance finale
  intermediate?: string; // intermédiaire produit par la section entière
}
```

Les identifiants de tâches sont stables et explicites : `s0.prep`, `s1.prep.pâte`, `s0.3`, `s0.3.t0`.

## `project`

```typescript
function project(recipes: ProjectionInput[], context: ProjectionContext): ProjectedPlan

interface ProjectionInput {
  graph: TaskGraph;
  title?: string;
  options?: LayoutOptions;
}

interface ProjectionContext {
  serveAt: string;        // date-heure locale cible ("2026-10-11T13:00") dans timeZone
  timeZone: string;       // identifiant de fuseau IANA ("Europe/Paris")
  availability: Availability;
  now?: string;           // instant ISO ou heure locale de référence pour START_IN_PAST (par défaut, aucune vérification relative à l'horloge)
}

interface Availability {
  daily: TimeRange[];                               // plage quotidienne par défaut
  weekdays?: Partial<Record<Weekday, TimeRange[]>>; // "mon" … "sun" ; [] indique une indisponibilité complète
  dates?: Record<string, TimeRange[]>;              // "2026-10-09" ; surcharge prioritaire sur weekdays
}

interface TimeRange {
  start: string;
  end: string;            // "08:00"–"22:00" ; une heure de fin antérieure au début traverse minuit
}
```

Positionne l'ordonnancement d'une recette sur le calendrier réel afin d'achever la préparation à l'heure de service cible. Les durées passives élastiques sont ajustées pour que le travail actif s'insère dans les plages de disponibilité de l'utilisateur.

L'algorithme de résolution des conflits est glouton et déterministe (sans recherche d'optimum global). Bien qu'il accepte en entrée une liste de recettes, seule la première est planifiée actuellement (les recettes supplémentaires déclenchent le diagnostic `MULTI_RECIPE_UNSUPPORTED`). Un fuseau horaire IANA invalide ou une heure de service mal formée lève une exception `RangeError`.

```typescript
const plan = project(
  [{ graph: tasks, title: 'Pain de campagne' }],
  {
    serveAt: '2026-10-11T13:00',
    timeZone: 'Europe/Paris',
    availability: {
      daily: [{ start: '08:00', end: '22:00' }],
      weekdays: { sun: [{ start: '09:00', end: '20:00' }] },
    },
  },
);
```

### `ProjectedPlan`

```typescript
interface ProjectedPlan {
  serveAt: string;
  timeZone: string;
  recipes: {
    title?: string;
    miseEnPlace: 'perSection' | 'upfront' | 'perSession'; // le mode dans lequel ce plan a été établi
    blocks: ProjectedBlock[];     // blocs planifiés avec start/end au format ISO 8601 (UTC)
    sessions: ProjectedSession[]; // et startLocal/endLocal : heure locale dans le fuseau ("2026-10-10T21:40")
  }[];
  adjustments: RestAdjustment[];  // ajustements appliqués aux temps passifs élastiques
  unavailable: { start: string; end: string }[]; // périodes d'indisponibilité intersectant la plage du plan
  diagnostics: ProjectionDiagnostic[];
}

interface RestAdjustment {
  task: string;
  from: number; // minutes
  to: number;
  reason: "avoid-unavailable";
}

type ProjectionDiagnostic =
  | { code: "ACTIVE_OUTSIDE_AVAILABILITY"; task: string; local: string; rest?: string }
  | { code: "ACTIVE_BLOCK_EXCEEDS_AVAILABILITY"; tasks: string[]; minutes: number; largest: number }
  | { code: "SESSION_DAY_MISMATCH"; day: number; expected: string; actual: string }
  | { code: "START_IN_PAST"; start: string; now: string }
  | { code: "MULTI_RECIPE_UNSUPPORTED"; recipes: number };
```

Ces diagnostics dépendent du contexte d'exécution et des disponibilités de l'utilisateur : ils sont portés par le résultat de `project()` et ne constituent pas des avertissements de compilation. Consultez [Planifier en heures réelles](/fr/docs/explanation/planning-in-real-time/#diagnostics-et-contraintes-non-résolues) pour le détail de chaque diagnostic.

## `runSheet`

```typescript
function runSheet(
  source: ProjectedPlan | Schedule,
  options?: { graph?: TaskGraph; title?: string; context?: ProjectionContext },
): RunSheet
```

Génère la structure de données du planning de préparation : découpage par journée pour chaque recette, puis, au sein de chaque journée, identification des **passages en cuisine** actifs et des **fils** passifs qui se poursuivent de façon autonome.
- Un `ProjectedPlan` produit une planification calendaire horodatée (`mode: "calendar"`) ;
- Un `Schedule` seul produit une structure temporelle relative exprimée en jours avant le service (`mode: "relative"`).

Lorsque les options `graph` et `context` sont fournies (dans le cas d'une projection calendaire), chaque passage se voit attribuer sa marge d'anticipation. Les définitions des termes clés sont détaillées dans [Le moteur d'ordonnancement](/fr/docs/explanation/engine/scheduler/#de-la-chronologie-au-planning-de-préparation).

```typescript
interface RunSheet {
  mode: "calendar" | "relative";
  serveAt?: string;            // plans calendaires uniquement
  timeZone?: string;
  recipes: { title?: string; miseEnPlace: MiseEnPlaceMode; days: RunSheetDay[]; totalWork: number }[]; // totalWork : durée totale de travail actif (en minutes)
  adjustments: RunSheetAdjustment[]; // attentes allongées ou raccourcies, avec leur section et leur jour
  diagnostics: ProjectionDiagnostic[];
}

interface RunSheetDay {
  date?: string;               // "2026-10-10", avec une heure de service
  daysBefore: number;          // 0 le jour du service, 1 la veille...
  passages: RunSheetPassage[]; // les passages en cuisine, dans l'ordre
  threads: RunSheetThread[];   // processus passifs se poursuivant après un passage
  entries: RunSheetEntry[];    // chaque bloc du jour, dans l'ordre
}

interface RunSheetPassage {
  start: number;               // minutes avant le service (<= 0), exactes
  end: number;
  startLocal?: string;         // "2026-10-10T21:40", avec une heure de service
  endLocal?: string;
  sections: number[];          // sections avec du travail dans le passage, dans l'ordre de la recette
  tasks: string[];             // identifiants des préparations et étapes du graphe
  window?: { advance: number; earliest: number; earliestLocal: string }; // fenêtre d'anticipation (calculée dès 15 min)
  fixedBy?: { task: string; section: number; planned: number; before: "service" | "passage"; sections?: number[] };
}

interface RunSheetThread {
  passage: number;             // indice dans les passages du jour
  task: string;
  section: number;
  step?: number;
  track?: string;
  from: number;                // minutes avant le service
  to: number;
  planned: number;             // minutes, ajustements compris
  fromLocal?: string;
  toLocal?: string;
  range?: { min: number; max: number }; // la fourchette écrite (avec `graph`)
}
```

Un **jour** est une session de la recette ; avec une heure de service, une session qui s'étale sur plusieurs dates est racontée un jour par date, et un passage qui franchit minuit reste entier à la date où il commence. `RunSheetEntry` est l'enregistrement par bloc (`kind`, `active`, `from`, `to`, `minutes`, `startLocal`, `adjustment?`…).

Les mots et la mise en page n'y sont **pas** : `@gram-lang/renderer` les écrit (`runSheetToText`, `runSheetToMarkdown`, `runSheetToHTML`, `runSheetToPrintHTML`, `describeRunSheet` ; voir la [référence du renderer](/fr/docs/reference/api/renderer/)).

## `findServeTimes` et `earliestServe` <Since v="1.4.0" />

Les deux reposent sur `project()` : elles essaient des heures de service et gardent celles qui peuvent être suivies. Une heure est rejetée quand le plan a un problème non résolu, un début déjà passé compris, et chaque rejet porte ses raisons.

```typescript
function tryServeAt(input: ProjectionInput, context: ProjectionContext, serveAt: string): ServeCandidate;

function findServeTimes(
  input: ProjectionInput,
  context: ProjectionContext,        // demande `now` pour rejeter les débuts passés
  options: {
    from: string;                    // "2026-10-12" ou "2026-10-12T08:00", local
    to: string;                      // une simple date désigne sa journée entière
    mealTimes?: string[];            // par défaut DEFAULT_MEAL_TIMES = ["12:30", "20:00"]
    limit?: number;                  // par défaut 5
  },
): { candidates: ServeCandidate[]; rejected: ServeCandidate[] };

function earliestServe(
  input: ProjectionInput,
  context: ProjectionContext,        // `now` requis (ou `options.from`)
  options?: { from?: string },
): { found?: ServeCandidate; searchedUntil: string };

interface ServeCandidate {
  serveAt: string;                   // local
  ok: boolean;
  reasons: ProjectionDiagnostic[];
  adjustments: number;               // attentes allongées ou raccourcies
  passages: number;                  // passages en cuisine
  startsAt?: string;                 // local, première tâche
  plan: ProjectedPlan;
}
```

Les `candidates` sont classés : moins d'ajustements, puis moins de passages, puis le plus tôt. `earliestServe()` part de la durée la plus courte de la recette après le présent et avance par pas de cinq minutes pendant `EARLIEST_SERVE_HORIZON_DAYS` jours (14). Les mots pour les deux sont `describeServeTimes()` et `describeEarliestServe()` du renderer ; `gram plan --find` est la même recherche.

## Options et utilitaires

```typescript
type MiseEnPlaceMode = "perSection" | "upfront" | "perSession";
const MISE_EN_PLACE_MODES: readonly MiseEnPlaceMode[];
const DEFAULT_MISE_EN_PLACE_MODE: MiseEnPlaceMode; // "perSection"
function isMiseEnPlaceMode(value: unknown): value is MiseEnPlaceMode;

type RestChoice = "shortest" | "balanced" | "longest";
const REST_CHOICES: readonly RestChoice[];
const DEFAULT_REST_CHOICE: RestChoice; // "shortest"
function isRestChoice(value: unknown): value is RestChoice;

const WEEKDAYS: readonly ["mon", "tue", "wed", "thu", "fri", "sat", "sun"];

const PASSAGE_GAP_MINUTES = 60;          // une attente de cette durée termine un passage en cuisine
const WINDOW_MIN_MINUTES = 15;          // une marge plus courte n'est pas dite
const DEFAULT_MEAL_TIMES: string[];     // ["12:30", "20:00"]
const EARLIEST_SERVE_HORIZON_DAYS = 14;

// Manipulation de dates sans dépendance tierce, adossée à un fuseau explicite
function parseLocalIso(value: string, timeZone: string): number; // "2026-10-11T13:00" → minutes depuis l'époque Unix (UTC)
function parseInstant(value: string, timeZone: string): number;  // instant ISO (avec 'Z' ou décalage UTC) ou heure locale
function toLocalIso(utcMinutes: number, timeZone: string): string; // → "2026-10-11T13:00"
function toUtcIso(utcMinutes: number): string;                    // → "2026-10-11T11:00:00Z"
```

Lors du passage à l'heure d'été, une heure locale inexistante (par exemple 02:30 lors de l'avance des horloges) est automatiquement décalée vers la première heure valide suivante ; lors du passage à l'heure d'hiver, une heure ambiguë (apparaissant deux fois lors du recul) est résolue sur sa première occurrence.
