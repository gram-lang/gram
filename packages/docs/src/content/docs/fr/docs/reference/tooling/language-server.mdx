Le Serveur de Langage Gram (`@gram-lang/language-server`) est le moteur d'analyse sous-jacent de l'intégration de Gram dans vos éditeurs de code. En implémentant le standard **Language Server Protocol (LSP)**, il fournit des fonctionnalités d'IDE avancées pour les fichiers `.gram` sur une multitude d'éditeurs (VS Code, Neovim, Helix, etc.).

## Architecture

Le serveur s'exécute comme un processus persistant en arrière-plan qui analyse vos fichiers `.gram` à l'aide des paquets `@gram-lang/parser`, `@gram-lang/kitchen` et `@gram-lang/scheduler`.

**Flux de traitement en temps réel :**
<Steps>
1. **Éditeur** ➔ Transmet les modifications du document à chaque frappe au clavier.

2. **Serveur de langage** ➔ Intercepte les deltas et sollicite la recompilation en mémoire de l'AST par le compilateur Kitchen.

3. **Compilateur Gram** ➔ Analyse la structure, résout les dépendances, ordonnance le rétro-planning ALAP et émet les diagnostics d'intégrité et de planification.

4. **Serveur de langage** ➔ Traduit ces données en charges utiles LSP standardisées (Diagnostics, Jetons sémantiques, Inlay Hints) et les renvoie à l'éditeur.
</Steps>

## Utiliser le serveur dans n'importe quel éditeur

<Since v="1.6.0" />

Tout éditeur qui parle le LSP sur stdio peut faire tourner le serveur : Neovim, Helix, Emacs (eglot ou lsp-mode), Zed, Sublime Text… Installez-le, puis indiquez à l'éditeur l'une de ces deux commandes pour les fichiers `.gram` :

```bash
npm install -g @gram-lang/language-server
gram-language-server --stdio

# ou, si la CLI est déjà installée :
gram lsp
```

Les deux lancent le même serveur. Stdio étant le transport par défaut, `--stdio` est facultatif ; il reste accepté pour les éditeurs qui l'ajoutent d'office. `gram-language-server --version` affiche la version et `--help` la liste des options, sans démarrer le serveur.

Dans la requête `initialize`, envoyez `initializationOptions: { views: false }`. L'éditeur profite alors de toutes les fonctionnalités standard décrites plus bas (diagnostics, complétion, survol, formatage, renommage, coloration sémantique…), sans rien recevoir qu'il ne saurait afficher : pas de rendu HTML à chaque frappe, pas de notification `gram/*`, pas de Code Lens. La page [Éditeurs pris en charge](/fr/docs/reference/tooling/editors/) donne la configuration toute prête pour Neovim, Helix, Emacs, Sublime Text et les IDE JetBrains.

Le serveur n'envoie au client que les requêtes que celui-ci a déclaré comprendre :

- il n'enregistre sa surveillance de fichiers (`.gram/config.yaml`, `.gram/ingredients.yaml` et les fichiers `.gram`) que si le client annonce `workspace.didChangeWatchedFiles.dynamicRegistration` ; un client qui surveille lui-même ces fichiers peut toujours envoyer `workspace/didChangeWatchedFiles` ;
- il ne lit les réglages `gram` que si le client annonce `workspace.configuration`, et s'en tient sinon aux valeurs par défaut ;
- il ne rafraîchit les annotations en ligne (*inlay hints*) que si le client annonce `workspace.inlayHint.refreshSupport`.

Un éditeur qui ne transmet que `rootUri`, sans dossiers d'espace de travail, trouve malgré tout la base d'ingrédients du projet.

Pour arrêter le serveur, envoyez `shutdown`, attendez sa réponse, puis seulement `exit` : le serveur s'arrête dès qu'il reçoit `exit` ou que son entrée standard se ferme, sans terminer les réponses en cours.

### Les trois modes de vues

L'option `views` détermine ce que le serveur calcule en plus des fonctionnalités standard :

| `initializationOptions.views` | Ce que le serveur rend | Pour qui |
|---|---|---|
| `true` | Uniquement les sorties que le client déclare ouvertes, via le [protocole des vues](#protocole-des-vues). La réponse à `initialize` les liste dans `gramViews` et annonce le Code Lens. | Un éditeur doté de volets d'affichage, comme l'extension VS Code. |
| `false` | Rien : seulement les fonctionnalités standard. | Un éditeur sans volet d'affichage. |
| absente (ou toute autre valeur que `true` ou `false`) | <Since type="deprecated" v="1.4.0" /> L'aperçu de chaque document ouvert, affiché ou non, via les [notifications historiques](#notifications-pour-les-clients-antérieurs), jusqu'à la version 2.0.0. | Les clients écrits avant le protocole des vues. |

Un client lancé avec `views: false` qui envoie ensuite `gram/setOpenViews` bascule sur le protocole des vues pour les sorties qu'il désigne.

## Fonctionnalités LSP supportées

Le Serveur de Langage Gram implémente les capacités standardisées suivantes :

| Capacité LSP | Implémentation Gram |
|---|---|
| **Diagnostics** | Remontée en temps réel des erreurs de syntaxe, des incohérences structurelles (dépendances circulaires) et des avertissements d'ordonnancement (`DAY_OVERFLOW`, `DURATION_OUT_OF_RANGE`, `TRACK_CONTENTION`). |
| **Semantic Tokens** | Coloration sémantique pilotée par l'AST pour les modificateurs, unités, températures, opérateurs de proportion (`/`) et ingrédients composites. |
| **Completion** | Autocomplétion contextuelle des ingrédients de la base, unités canoniques et variables intermédiaires. Propose uniquement les unités de temps dans `~{…}`, relance la complétion d'unités après `+` ou `-` dans les sommes, et suggère les cibles `@&` / `&` (et unités de poids après `/`) dans les proportions. Sur une ligne `@use`, complète le chemin de l'import, puis les exports du module : son export par défaut après `as &`, et dans `as { … }` les sections exportées qui ne sont pas encore importées <Since v="1.6.0" />. |
| **Hover** | Affiche le profil nutritionnel et les conversions volume-masse au survol des ingrédients. Sur un minuteur, indique la durée interprétée (`~{1h30}` → `1 h 30 min`) ; sur une ancre de section, l'anticipation et l'ouverture d'une journée ; sur une somme ou une proportion, le total combiné (`{1 cup + 1 tbsp}` → `= 17 tbsp`) ou le détail par famille, la masse ou la raison d'un éventuel refus. |
| **Go to Definition** | Navigation directe depuis une référence intermédiaire (`&ref`, y compris dans une proportion) vers sa déclaration source (`->&ref`). |
| **Find References** | Recherche toutes les utilisations d'une variable intermédiaire à travers le document (proportions comprises). |
| **Rename** | Renommage atomique d'une variable intermédiaire dans tout le fichier (proportions comprises). |
| **Document Highlight** | <Since v="1.6.0" /> Quand le curseur est sur un nom, met en évidence ses autres occurrences dans le fichier : toutes les mentions d'un ingrédient, reconnues comme le fait la compilation (alternatives, parent d'un composite et cibles `@&` des proportions et pourcentages compris), ou la déclaration d'une variable intermédiaire (`->&`, `@use … as &`) avec ses utilisations (`&ref`, cibles `&`). |
| **Document Link** | <Since v="1.6.0" /> Transforme le chemin de chaque `@use "…"` en lien vers le module qu'il désigne (`Ctrl+Clic`), alias compris. Un module introuvable n'a pas de lien. |
| **Code Actions** | Corrections rapides (*quick fixes* : déclaration d'une variable manquante, conversion volume-masse, insertion du `+` manquant ou application du total suggéré dans une somme, remplacement de `oz` après un volume par `fl oz`). |
| **Document Formatting** | Normalisation syntaxique via `@gram-lang/format`. |
| **Inlay Hints** | Affiche la durée totale sur la ligne `title:` (selon `gram.miseEnPlace` et `gram.rests`), ainsi que les valeurs résolues (`= 5`, `= 16 g`, `= 24 min`) après chaque proportion avec unités ou temps proportionnel. |
| **Code Lens** | VS Code (`views: true`) uniquement : un bouton au-dessus du document ouvre l'aperçu en direct (`▶ Aperçu`, dans la langue de l'éditeur). |
| **Document Symbol** | Alimente la vue Plan (*Outline*) pour naviguer entre les sections. |
| **Folding Range** | Permet de replier le frontmatter YAML et les sections `##`. |

## Réglages

Le serveur lit la section de configuration `gram` (`workspace/configuration`) au démarrage, puis à chaque notification `workspace/didChangeConfiguration`. Toute valeur absente ou non reconnue bascule automatiquement sur sa valeur par défaut : une erreur de saisie ne rend donc jamais une vue vierge.

- Les réglages de vue (`gram.miseEnPlace`, `gram.rests`, `gram.comments`, `gram.stepQuantities`, `gram.nutritionBasis`, `gram.bakersMathOnly`, `gram.clock`) actualisent l'affichage des recettes ouvertes directement à partir de leur résultat de compilation.
- Les réglages de l'analyseur (`gram.bakersMath`, `gram.massStandardization`, `gram.yieldCalculation`, `gram.nutritionEstimation`) déclenchent une nouvelle analyse des recettes ouvertes et mettent à jour les diagnostics associés.
- `gram.ingredientDatabase.path` recharge la base d'ingrédients depuis le disque.

L'ensemble des options et valeurs par défaut correspond à la configuration de l'[extension VS Code](/fr/docs/reference/tooling/vscode-extension/), définie de façon centralisée dans le moteur de rendu (`VIEW_SETTINGS`, `RECIPE_SETTINGS`).

## Protocole des vues

En complément des requêtes standardisées du protocole LSP, le serveur génère directement les vues d'une recette (la recette, le plan de marche) ainsi que ses inspecteurs (l'AST et le JSON compilé) prêts à être affichés par l'éditeur. Le serveur ne calcule que les vues actuellement ouvertes dans le client : un panneau masqué n'induit aucun surcoût de calcul.

Le client active ce protocole en transmettant `initializationOptions: { views: true }` lors de la requête `initialize`, puis dialogue avec le serveur via trois notifications spécifiques et deux requêtes :

| Notification | Sens | Contenu |
|---|---|---|
| `gram/setOpenViews` | Client ➔ Serveur | `{ uri, viewIds }` : ensemble complet des identifiants de vues ouvertes pour ce document (`[]` si aucun volet n'est ouvert). Le serveur émet immédiatement les contenus correspondants. |
| `gram/setSession` | Client ➔ Serveur | `{ uri, serveAt?, scale?, stock?, bakersReference? }` : paramètres contextuels de la session de travail. `serveAt` est une date et heure locale (`"2026-10-11 13:00"`), `scale` spécifie un facteur `{ type: "factor", value }` ou une cible `{ type: "target", id, qty, unit }`, et `stock` liste les URI des modules déjà prêts en cuisine. Tout paramètre non reconnu est ignoré ; un objet vide réinitialise la session. |
| `gram/viewUpdated` | Serveur ➔ Client | `{ uri, outputId, kind, state, ... }` : émis pour chaque sortie ouverte lors de son affichage initial, puis actualisé après chaque modification ou ajustement des réglages. |
| `gram/serveTimes` (requête) | Client ➔ Serveur | `{ uri }` → `{ candidates, rejected, earliest }` ou `null` : les heures de service à proposer à côté d'un champ d'heure de service, comme le fait le studio en ligne. `candidates` regroupe les heures qui conviennent sur les sept prochains jours aux heures de repas du projet (`mealTimes`, par défaut 12:30 et 20:00), les meilleures d'abord, chacune sous la forme `{ serveAt, label, title }` ; `rejected` explique en toutes lettres pourquoi les autres ne conviennent pas ; `earliest` vaut `{ serveAt, label, text }`, le moment le plus proche où la recette peut être prête si vous commencez maintenant. `null` si la recette n'a rien à planifier. Ne l'interrogez que lorsque les suggestions sont affichées : elle planifie quelques dizaines d'horaires. |
| `gram/sessionChoices` (requête) | Client ➔ Serveur | `{ uri }` → `{ ingredients, imports, bakersMath, scaleError? }` ou `null` : ce que proposent les réglages de séance, lu sur la recette telle qu'elle est écrite pour que les choix ne bougent pas avec l'échelle. `ingredients` reprend la liste de courses (`{ id, name, qty?, unit? }`, pour une quantité visée ou la référence boulangère), `imports` tous les imports `@use`, y compris imbriqués (`{ uri, specifier }`, l'`uri` étant celle à placer dans `stock`), `bakersMath` indique si `gram.bakersMath` est actif, et `scaleError` explique pourquoi l'échelle de la session n'a pas pu s'appliquer. `null` tant que la recette ne compile pas. |

La réponse à la requête `initialize` énumère l'ensemble des sorties disponibles dans `capabilities.experimental.gramViews` : `outputs` précise l'`id`, le `kind` et le `label` traduit de chaque vue (dans la langue de l'éditeur), ainsi que, pour une vue, ce qu'elle lit de l'ordonnancement (`needs` : une vue qui lit `runSheet` est calée dans le temps, et un client lui propose donc le choix de l'heure de service), tandis que `strings` fournit les libellés de l'interface environnante (`strings.serving` pour le champ d'heure de service et ses suggestions, `strings.session` pour l'échelle, la référence boulangère et le stock). Les identifiants correspondent aux sorties déclarées par le moteur de rendu : `recipe` et `runSheet` (`kind: "renderer"`), ainsi que `ast`, `json` et `json-tree` (`kind: "inspector"`). Un client qui construit dynamiquement son menu de vues à partir de cette liste prend ainsi en charge toute nouvelle vue ajoutée au moteur sans nécessiter de mise à jour spécifique.

- Lorsque `state: "ok"`, `payload` contient le code HTML rendu de la vue, ou `null` si la recette ne comporte aucun contenu correspondant (par exemple un <Term id="runSheet" /> pour une recette dépourvue d'étapes minutées). Pour un inspecteur, `payload` contient `{ presentation, language, text }` : du texte formaté pour un volet de code (`presentation: "code"`, coloré en `json` ou en `scheme`), ou une structure HTML pour une arborescence interactive (`presentation: "tree"`).
- Lorsque `state: "paused"`, les erreurs de compilation empêchent la génération des vues et `payload` est omis : l'éditeur doit conserver le dernier état valide affiché et signaler l'erreur via la propriété `error` (`title`, `description`, `code`, `message` et `range`). Le titre de l'erreur est traduit selon la locale de l'éditeur (`locale` d'`initialize`). Les détails complets de l'erreur demeurent accessibles via les diagnostics LSP habituels.

La session est gérée par document en mémoire vive : elle est réinitialisée à la fermeture du fichier ou au redémarrage du serveur, et n'est jamais enregistrée dans les fichiers de configuration. Lorsqu'une heure de service est indiquée, le plan de marche est calé sur le calendrier dans le fuseau horaire du projet (`timezone` dans `.gram/config.yaml`, sinon celui du système) et selon ses disponibilités (`availability`, sinon toute la journée, y compris si le réglage est illisible) ; sans heure de service, il est présenté en jours relatifs avant dégustation. Les heures suivent `gram.clock` : en `auto`, le réglage `clock` de `.gram/config.yaml`, sinon la région de la locale du serveur (`LC_ALL`, puis `LC_TIME`, puis `LANG` ; sous Windows, la région du système) <Since v="1.5.0" />. Si des paramètres de session (`scale`, `stock` ou `bakersReference`) sont définis, les vues sont recompilées en intégrant ces options, tandis que les diagnostics, le survol et les annotations en ligne (*inlay hints*) continuent d'évaluer la recette telle qu'elle est rédigée. Si une mise à l'échelle ne peut pas être résolue, les vues conservent leurs proportions d'origine.

### Notifications pour les clients antérieurs

Les clients qui ne transmettent aucune option `views` et n'envoient jamais `gram/setOpenViews` continuent de recevoir les aperçus de chaque document ouvert via les notifications historiques ci-dessous sous la forme d'un objet `{ uri, html }`, que les volets soient affichés ou non dans l'éditeur. Le serveur consigne une seule fois un avertissement de dépréciation dans son journal.

| Notification | Contenu |
|---|---|
| `gram/previewUpdated` | <Since type="deprecated" v="1.4.0" /> Rendu HTML de l'aperçu en direct, ou panneau d'erreur lorsque la recette ne compile pas. Supprimée en version 2.0.0 : migrez vers `gram/viewUpdated` avec la sortie `recipe`. |
| `gram/ganttUpdated` | <Since type="deprecated" v="1.4.0" /> Rendu HTML du diagramme de Gantt historique. Émis jusqu'en version 2.0.0 pour préserver la compatibilité avec les clients tiers (l'extension officielle VS Code ne l'écoute plus). |

Pour sortir de ce mode sans adopter le protocole des vues, il suffit d'envoyer `initializationOptions: { views: false }` : le serveur cesse alors de calculer ces vues et d'émettre ces notifications, sans plus aucun avertissement.
