Gram fonctionne dans tout éditeur qui parle le Language Server Protocol, avec deux niveaux de prise en charge.

## Deux niveaux de prise en charge

- **Support officiel** : [VS Code et ses dérivés](#vs-code-et-ses-dérivés), avec l'extension publiée sur le VS Code Marketplace et sur Open VSX. L'extension pour [Zed](#zed) va bientôt s'y ajouter. Ces intégrations sont maintenues et vérifiées par le projet.
- **Configurations LSP communautaires** : [Neovim](#neovim), [Helix](#helix), [Emacs](#emacs), [Sublime Text](#sublime-text) et les [IDE JetBrains](#ide-jetbrains). Elles ne reposent que sur le protocole standard : l'éditeur lance `gram-language-server --stdio` et envoie `views: false`. Chacune est une base qui fonctionne, d'où partir, sans maintenance propre à chaque éditeur. Retours et pull requests de celles et ceux qui utilisent ces éditeurs sont les bienvenus, sur le [suivi des tickets](https://git.gram-lang.org/gram-lang/gram/issues) ou directement dans le dossier `editors/` du dépôt.

Les configurations communautaires ne sont pas toutes vérifiées de la même façon :

- chacune passe un test de contrat à chaque modification (`editors.test.ts` : la commande, `views: false`, l'extension `.gram` et les commentaires, le même commit de la grammaire Tree-sitter pour Helix et Neovim), et le serveur lui-même est testé tel que le voit n'importe quel client LSP ;
- **Neovim et Emacs** sont en plus pilotés par leur propre client LSP dans un conteneur (`editors/smoke/run.sh` : diagnostics, complétion, survol, formatage, renommage), et **Helix** y vérifie qu'il lit la configuration et trouve le serveur. Helix et Neovim y compilent aussi la grammaire Tree-sitter, et Neovim vérifie les couleurs et les replis qu'elle donne ;
- **Sublime Text et les IDE JetBrains** sont fournis tels quels, sans banc d'essai dans l'éditeur lui-même. Leurs écrans de réglages changent d'une version à l'autre : c'est leur propre documentation qui fait foi pour l'emplacement de chaque champ.

## Ce que chaque éditeur sait faire

| Éditeur | Prise en charge | Coloration | Diagnostics | Complétion | Survol | Formatage | Renommage | Aperçu |
|---|---|---|---|---|---|---|---|---|
| [VS Code et ses dérivés](#vs-code-et-ses-dérivés) | Officielle | Complète (grammaire TextMate et jetons sémantiques) | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| [Zed](#zed) | Officielle, bientôt disponible | Complète (Tree-sitter) | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| [Neovim](#neovim) | Communautaire, testée en conteneur | Complète avec Tree-sitter, partielle avec le serveur seul (jetons sémantiques) | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| [Helix](#helix) | Communautaire, configuration vérifiée en conteneur | Complète (Tree-sitter) | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| [Emacs](#emacs) | Communautaire, testée en conteneur | Commentaires seulement | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| [Sublime Text](#sublime-text) | Communautaire, telle quelle | Complète (grammaire TextMate) | ✓ | ✓ | ✓ | ✓ | ✓ | — |
| [IDE JetBrains](#ide-jetbrains) | Communautaire, telle quelle | Partielle (jetons sémantiques), complète avec le bundle TextMate | ✓ | ✓ | ✓ | ✓ | ✓ | — |

Les colonnes de fonctionnalités disent ce que le serveur envoie ; pour Sublime Text et les IDE JetBrains, elles ne sont pas vérifiées dans l'éditeur.

- **La coloration partielle** vient des jetons sémantiques du serveur : sigles et noms (`@farine`, `#bol`, `&pâte`), accolades, modificateurs, actions et commentaires prennent une couleur, mais pas le contenu des accolades (quantités, durées, températures). Elle attend aussi la réponse du serveur, un instant après l'ouverture du fichier.
- **La coloration Tree-sitter** vient de [tree-sitter-gram](https://github.com/gram-lang/tree-sitter-gram), une grammaire qu'on compile une fois sur sa machine : tout prend une couleur, l'intérieur des accolades compris, dès l'ouverture du fichier. Chaque élément y joue le même rôle que dans la grammaire de VS Code : avec un thème proche, les couleurs sont les mêmes.
- **L'aperçu** de la recette et du <Term id="runSheet" /> n'existe pour l'instant que dans VS Code.

## Support officiel

### VS Code et ses dérivés

Installez l'extension **Gram - Recipe Language** depuis le [VS Code Marketplace](https://marketplace.visualstudio.com/items?itemName=gram-lang.gram-lang), ou depuis [Open VSX](https://open-vsx.org/extension/gram-lang/gram-lang) pour VSCodium, Cursor, Windsurf ou Positron. Elle embarque le serveur : rien d'autre à installer. Voir [Extension VS Code](/fr/docs/reference/tooling/vscode-extension/).

### Zed

Bientôt disponible : l'extension **Gram** attend sa place dans le catalogue d'extensions de Zed. Une fois qu'elle y sera, installez-la depuis la page des extensions de Zed, puis ouvrez une recette :

- les couleurs et le plan des sections viennent de la grammaire [tree-sitter-gram](https://github.com/gram-lang/tree-sitter-gram), que Zed compile lui-même ;
- diagnostics, complétion, survol, formatage et renommage viennent du serveur de langage. L'extension prend le `gram-language-server` de votre `PATH` s'il y en a un ; sinon, elle télécharge d'elle-même `@gram-lang/language-server` depuis npm et le lance avec le Node de Zed. Il lui faut la version 1.6.0 ou plus récente.

Le code de l'extension se trouve dans le dépôt [zed-gram](https://github.com/gram-lang/zed-gram).

## Configurations LSP communautaires

Ces configurations sont des points de départ : adaptez-les à votre installation, et partagez ce que vous améliorez.

### Installer le serveur

Chaque éditeur ci-dessous lance le serveur comme une commande. Installez-le une fois pour toutes :

```bash
npm install -g @gram-lang/language-server
```

Ces configurations lancent `gram-language-server --stdio`. Si la CLI est déjà installée, `gram lsp` lance le même serveur : remplacez la commande par celle-ci si vous préférez.

Toutes envoient aussi `views: false` : ces éditeurs n'ont pas de panneau d'aperçu, le serveur ne calcule donc aucune vue et s'en tient aux fonctionnalités standard du LSP.

Un éditeur lancé depuis un menu ne voit pas toujours le `PATH` de votre terminal. S'il ne trouve pas `gram-language-server`, donnez-lui le chemin complet qu'affiche `which gram-language-server` (`where gram-language-server` sous Windows).

Testé avec Neovim 0.11.6 et 0.12.6, couleurs Tree-sitter et replis compris.

#### Couleurs Tree-sitter et repli des sections

Avec le serveur seul, quantités, durées et températures restent sans couleur. `hx --health gram` vérifie que Helix lit la configuration et trouve le serveur. La complétion s'affiche d'elle-même pendant la frappe ; <kbd>Espace</kbd> <kbd>k</kbd> affiche le survol, <kbd>Espace</kbd> <kbd>r</kbd> renomme, `:format` formate et <kbd>Ctrl</kbd>+<kbd>c</kbd> commente avec `//`.

Helix ne se sert pas des jetons sémantiques : ses couleurs viennent de la grammaire tree-sitter-gram, déclarée à un commit précis par le bloc `[[grammar]]`. Helix la compile, mais n'installe pas ses requêtes, qui disent quoi colorer. Une fois, puis à chaque fois que cette page passe à un commit plus récent :

```bash
hx --grammar fetch
hx --grammar build
mkdir -p ~/.config/helix/runtime/queries/gram
cp ~/.config/helix/runtime/grammars/sources/gram/queries/helix/*.scm ~/.config/helix/runtime/queries/gram/
```

- La compilation demande `git` et un compilateur C et C++ : Helix 25.07 cherche `c++`, même pour une grammaire écrite en C.
- `hx --grammar fetch` récupère aussi toutes les autres grammaires que Helix connaît. Pour ne récupérer et compiler que celle de Gram, placez `use-grammars = { only = ["gram"] }` tout en haut de `languages.toml` : les autres grammaires restent alors telles quelles.
- `hx --health gram` affiche ensuite `Highlight queries: ✓`. Il affiche aussi `Tree-sitter parser: ✓` avant même la compilation : c'est la présence de `~/.config/helix/runtime/grammars/gram.so` qui compte.

Testé avec Helix 25.07 (configuration, serveur et requêtes vérifiés par `hx --health`, grammaire compilée en conteneur).
